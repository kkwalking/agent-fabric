# AgentFabric 当前功能闭环修复需求

请基于当前已经实现的 AgentFabric 代码继续修正。

本阶段目标不是增加新功能，而是确保当前已经暴露给用户的能力真正从控制面配置一直生效到 Harness 执行面。

当前整体架构已经基本稳定，包括：

* Provider
* Model
* Runtime
* Task
* Run
* Workspace
* Handoff
* RuntimeSessionRef
* Runtime Native State
* Execution Backend
* Agent Profile
* Execution Policy
* Local / Docker Runtime
* Pi / OpenCode Adapter
* Native Resume
* Cross-Harness Handoff

本阶段不要重新设计这些核心抽象。

重点解决以下现有功能未闭环问题。

---

## 1. 打通 Provider → Harness 执行链路

当前 Provider 已经支持配置：

* Provider Type
* Base URL
* API Key Secret
* Custom Headers
* Enabled / Disabled

但是这些配置必须真正进入 Pi / OpenCode 的实际执行环境。

用户通过 AgentFabric 创建 Provider 后，不应该还需要额外手工配置 Harness。

目标流程必须是：

Create Provider

→ 配置 API Key / Base URL / Headers

→ Create Model

→ Model 关联 Provider

→ Submit Run

→ AgentFabric 自动将 Provider 配置注入对应 Harness

→ Harness 成功调用目标模型

---

## 2. Provider Secret 自动注入

Provider 的 API Key 已经由 AgentFabric Secret 管理。

执行 Run 时，需要自动解析当前 Model 对应的 Provider，并将该 Provider 所依赖的 Secret 注入 Runtime。

用户不应该需要在 Task / Runtime 中再次手动添加相同 Secret。

需要保证：

Model

→ Provider

→ Provider API Key Secret

→ Runtime Execution Environment

形成完整链路。

---

## 3. Provider Base URL 必须生效

如果用户创建的是：

* OpenAI-compatible Provider
* Self-hosted Provider
* Proxy Provider
* Custom Endpoint

那么 Provider 中配置的 Base URL 必须真正传递给对应 Harness。

不能只把 Provider Name 传给 Pi / OpenCode。

Harness 最终实际访问的 Endpoint 必须与 AgentFabric Provider 配置一致。

---

## 4. Provider Custom Headers 必须生效

如果 Provider 配置了额外 HTTP Headers，需要在 Harness 支持的情况下将其传递到真实模型请求。

如果某个 Harness 无法直接支持某类 Provider 配置，需要明确标识该 Runtime / Harness 的 Provider Compatibility。

不要静默忽略用户已经保存的 Header 配置。

---

## 5. Provider Enabled 状态必须参与执行判断

如果 Provider 被 Disabled：

不能继续通过该 Provider 启动新的 Run。

需要在 Run 创建或准备阶段返回清晰错误。

不要等 Harness 启动后才因为认证或连接失败报错。

---

# 6. 打通 Model 配置

当前 Model 已经包含：

* Name
* Alias
* Parameters
* Capabilities
* Provider Reference

这些字段不能只停留在控制面。

执行 Run 时，需要由 Harness Adapter 消费当前 Runtime 真正支持的 Model Configuration。

---

## 7. Model Parameters 必须真正生效

如果用户配置：

* Temperature
* Max Tokens
* Reasoning / Thinking
* Context-related Parameters
* 其他 Harness / Provider 支持的 Model 参数

需要在对应 Harness 支持的情况下传递到实际模型调用。

AgentFabric 不要求所有 Harness 支持完全一致的参数。

但不能出现：

用户保存了 Model Parameters

→ UI / API 显示配置成功

→ 实际执行完全忽略

的情况。

---

## 8. 不支持的 Model 参数需要明确处理

对于 Harness 不支持的参数：

可以选择：

* Validation 阶段拒绝
* 标记为 Unsupported
* 忽略但明确警告

不要静默吞掉。

目标是让用户能够知道：

当前 Model 配置中哪些参数真正会影响执行。

---

# 9. 完善 Agent Profile 执行绑定

当前 Agent Profile 已经包含：

* Runtime
* Model
* Tools
* Env
* Secrets
* Policy
* System Instructions
* Resource Limits
* Workspace Config

这些字段应该在 Run 中真正生效。

---

## 10. Agent Profile System Instructions 必须进入 Harness

当前用户通过 Agent Profile 配置的：

`systemInstructions`

必须传递到实际 Agent Harness。

例如：

Senior Engineer Profile

包含：

“You are a senior engineer...”

那么 Pi / OpenCode 真正执行 Task 时必须接收到这段 Instruction。

不要仅保存 Profile Metadata。

---

## 11. Agent Profile Tools 必须参与最终 Tool Policy

Profile 中声明的 Tools 需要进入实际执行配置。

最终 Tool Set 可以由：

* Profile Tools
* Task / Run Tools
* Execution Policy

共同决定。

需要定义清晰的合并和限制规则。

不能出现 Profile 配置了 Tools，但执行 Harness 完全没有消费的情况。

---

## 12. Agent Profile 其他字段保持现有语义

继续确保以下已有能力真正生效：

* Env
* Secrets
* Runtime
* Model
* Resource Limits
* Workspace Config
* Policy

Profile 不应该只是一个 UI / CRUD 配置对象，而应真正成为 Run Configuration Preset。

---

# 13. 统一 Execution Policy Enforcement

当前 Execution Policy 已经包含多个限制字段。

需要确保实际 Runtime / Docker / Harness 使用的是统一解析后的最终 Policy，而不是不同模块分别读取不同来源。

Run 执行前应该先得到一个最终：

`ResolvedExecutionPolicy`

后续所有执行层只消费这一份最终结果。

---

## 14. Policy 合并必须统一

Policy 可能来自：

* Runtime defaults
* Agent Profile
* Task
* Run continuation override

需要定义并使用统一的优先级和 merge 结果。

Docker 和 Harness Adapter 不应该再次直接读取原始 Task Policy。

---

## 15. Shell Policy 必须对所有 Harness 一致生效

如果：

`shell = deny`

那么所有 Runtime 都应该禁止 Agent 使用 Shell / Command Execution 能力。

不能出现：

Pi 遵守

但 OpenCode 不遵守

的情况。

如果 Harness 无法实现严格限制，需要在 Runtime Capability 中明确反映。

---

## 16. Tool Permissions 必须对所有 Harness 一致生效

Execution Policy 中的：

`toolPermissions`

需要尽可能传递给对应 Harness。

对于不同 Harness，可以有不同 Adapter 实现方式。

但最终产品语义应该保持一致：

AgentFabric Policy 控制 Agent 可以使用哪些工具。

---

## 17. Filesystem Policy 必须真正控制 Workspace Mount

当前 Workspace Mount 的只读 / 可写行为需要基于最终 Execution Policy。

例如：

filesystem = read-only

→ Docker Workspace Mount 必须为只读。

filesystem = writable

→ 才允许写入。

不要继续使用 Runtime-specific 字段绕过统一 Policy。

---

## 18. Network Policy 必须使用最终 Resolved Policy

Docker Network Mode 和相关 Network Restriction 应根据最终 Run Policy 决定。

如果 continuation Run 覆盖了 Network Policy：

新的设置必须真正生效。

---

## 19. Resource Limits 必须使用最终 Resolved Configuration

以下限制都应来自最终合并后的运行配置：

* CPU
* Memory
* Timeout
* Max Tokens
* Max Cost
* Max Model Calls

不要出现 Task / Profile / Run Override 已更新，但 Docker / Harness 仍使用旧值的情况。

---

# 20. 修复 Keep-Alive Container 的状态边界

当前 Ephemeral Container 行为已经基本正确。

本阶段只需要修复 Keep-Alive 模式已有的边界问题。

不要新增 Warm Pool。

---

## 21. Keep-Alive Container 不应跨不相关 Task 复用状态

当前 Keep-Alive Container 的复用条件需要收紧。

有状态 Container 不应该仅根据：

Runtime + Workspace

就被另一个无关 Task 复用。

至少需要保证复用属于同一个逻辑执行上下文。

可以结合：

* Task
* Runtime
* Workspace
* Native Session Lineage

判断。

目标是避免：

Task A 留下的 Harness State

被 Task B 意外继承。

---

## 22. Keep-Alive 与 Warm Reuse 不要混淆

当前 Keep-Alive 的语义应该是：

> 保留当前任务 / Session 的运行环境，以便短时间继续。

不是：

> 把这个 Container 当成通用 Warm Pool 给其他 Task 使用。

本阶段不要实现 Warm Pool。

只需要保证 Keep-Alive 的状态边界正确。

---

# 23. 修复 Keep-Alive Cancel / Timeout

当一个 Keep-Alive Run 被：

* Cancel
* Timeout
* Abort

时，不能只终止本地 `docker exec` client。

需要保证 Container 内正在执行的 Harness Process 也停止。

不能出现：

Run 已显示 Cancelled

但 Container 内 Agent 仍继续执行。

---

## 24. Cancel / Timeout 后的 Container 处理

对于 Keep-Alive Container：

如果本次 Run 被异常终止，需要明确处理其后续状态。

至少要保证：

* Harness Process 已停止
* Container 不存在残留执行任务
* 不会把一个状态不确定的 Container 重新标记为安全可复用

必要时可以直接销毁该 Keep-Alive Container。

优先保证正确性，不要为了复用 Container 保留污染状态。

# 33. 最终验收场景

完成后，以下用户路径应该完整可运行。

Create Provider

→ Create Model

→ Create Pi / OpenCode Runtime

→ Create Workspace

→ Submit Task

→ Harness 使用 AgentFabric Provider Credential

→ Run Success

→ Events / Usage / Artifacts 正常

Create Provider

→ Create Model

→ Containerized Runtime

→ Attach Workspace

→ Save Workspace

→ Persist Native State

---

Run #1

→ Native Session Created

→ Runtime Native State Persisted

→ Container Destroyed

→ Save Workspace

→ Generate Handoff

## 场景 E：Agent Profile

Create Agent Profile

→ System Instructions

→ Tools

---

## 场景 F：Execution Policy

→ 不复用污染状态

# 34. 本阶段核心原则

请保持：

> **Existing configuration must affect execution.**

> **Control plane and execution plane must be connected.**

> **No silent configuration loss.**

> **Provider configuration belongs to AgentFabric, not manual Harness setup.**

> **Execution Policy must be enforced consistently.**

> **Keep-alive preserves the same execution context, not arbitrary cross-task state.**

> **Do not add new abstractions before existing behavior is fully closed-loop.**

本阶段完成的判断标准不是“CRUD 和字段都存在”，而是：

> **用户通过 AgentFabric 配置出来的 Provider、Model、Agent Profile、Policy、Runtime、Workspace，在真实 Pi / OpenCode Local 和 Docker 执行中都能实际生效，并能够通过 E2E 测试证明。**
