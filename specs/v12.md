# AgentFabric：Validation Agent 与返工循环（v12）

请基于当前 AgentFabric 项目的既有架构和代码实现以下功能。

本期的核心目标，是把 Validation 从「配置一组 shell 命令、看 exit code」改造成：

> **一个自然语言描述的验收标准，由一个独立的 Validation Agent 在全新容器里对 Task Agent 的产出做判定；判定不通过则打回 Task Agent 在原工作区上继续修改，循环最多三轮，仍不通过则整个 Task 失败。**

请先阅读现有代码（`packages/core/src/validation.ts`、`validationDocker.ts`、`supervisor.ts` 的 `runValidationStage` / `lifecycle`、`orchestrator.ts`、`provisioning.ts`、`policy.ts`）、`README.md` 与 `docs/validation.md`，在保持既有领域模型（Task / Run / Workspace / Runtime / Harness / Secret / Handoff）一致性的前提下设计与开发。

不要为了本需求改动 Handoff；不要引入并发队列 / 调度器；不要保留旧的 steps 机制的任何兼容路径（见「十、删除旧机制」，遵循 AGENTS.md「不为旧数据写兼容逻辑」）。

## 已定决策（用户明确拍板，实现时不得再改）

1. **循环预算**：最多 **3 次 judge 判定**（即最多 2 次返工）。判定的定义是「Validation Agent 产出了一个合法 verdict」；环境/基础设施类失败不消耗预算。
2. **手动重试重置预算**：`retry-validation`（Web / CLI / API）重跑一轮并**重置预算**——人工介入 = 给新预算。
3. **judge 模型默认跟随 Task**：Validation Agent 默认使用 Task 的 model；配置可单独指定。
4. **返工 run 自身失败直接终止 Task**：不重试返工、不拿半成品去判定。
5. **不注入 validation prompt，注入判定结论**：Task Agent 的返工指令里包含 Validation Agent 的结论（verdict），不包含原始 validation prompt。
6. **判定通过 tool call 提交**：为 Validation Agent 提供一个工具，在它完成判断时调用，产出机器可解析的确定性 verdict。
7. **完工 Pin 与工作区回放（外层硬约束）**：Validation Agent 不得提交任何代码——除 prompt 约束外，supervisor 在每次开发 run 完工时把工作区固定为一个**完工 commit（pin）**；判定结束后校验工作区仍停在 pin 上，出现任何意外 commit / 改动即**回放到 pin**（见「四·4.5」）。判定永远针对 pin 这个确定的 revision。

## 补充决策（用户已按推荐拍板，与「已定决策」同等，实现即按下列语义落地）

- **D1 · 返工 run 的会话形态**：**全新会话（`continuity: "new"`）+ 同一 Workspace + 结论注入**（可移植、无隐藏状态；结论里已含全部必要上下文）。备选（未采纳）：运行时支持原生会话恢复时 resume 原 Task Agent 的会话。
- **D2 · judge 对工作区的访问**：**只读挂载** `/workspace`，judge 需要跑构建/测试时自行在容器内复制到可写目录（`/tmp`）。原因见「九、安全与信任边界」；备选（未采纳）：supervisor 侧做快照拷贝后 rw 挂载（成本 = 整棵工作区复制）。
- **D3 · judge 未提交 verdict 的归类**：新增错误码 `validation-verdict-missing`（502），归入「环境坏了」→ 可自动重试、不消耗预算；判定不通过才是 `validation-failed`（400）。
- **D4 · judge run 超时的归类**：`validation-timeout`（400，不自动重试，可手动重试），与现有语义一致。
- **D5 · 返工 run 失败的 stage**：记 `failure.stage = "agent"`（返工 run 就是一次开发 run，它的失败就是 agent 失败），retry kind = agent → UI 给 **Retry Agent Run**。系统级瞬态自动重试（runtime-* 等既有 allowlist）保持适用。
- **D6 · `autoCommit: false` 与 validation 的组合**：**pin 仍然创建**——判定必须有确定的 revision 锚点、回放必须有 commit 可回放；README 明确「启用 validation 时，完工 commit 在开发 run 结束时创建」。`autoCommit` 此后只影响 finalization 是否追加 commit（工作区已在 pin 时提交干净，自然不再追加）。备选（未采纳）：拒绝该组合（`config-invalid`）。

## 一、目标与非目标

### 目标

1. Validation 的配置形态从「命令列表」变为「自然语言 prompt」；未配置 = 跳过（现状语义保留）。
2. 判定由独立 Validation Agent 在**全新容器**（新 Run）中完成，检查 Task Agent 是否完成了任务。
3. 判定结果结构化、机器可解析（tool call → verdict 文件 → 生成时冻结到记录）。
4. 判定不通过 → 自动打回：Task Agent 在同一 Workspace 上继续修改（新 Run），修改后重新判定；最多 3 次判定。
5. 3 次判定仍未通过 → Task 以 `validation-failed` 终止（附完整轮次记录）。
6. 手动重试（Retry Validation）重跑一轮并重置预算。
7. 观察性：每一轮的 judge run、verdict、返工 run、未满足项、证据都在 Task 记录与事件流里可查。

### 非目标

- 不改 Handoff。
- 不做多 judge 投票 / 人工审批节点 / 调度器。
- judge 不修改仓库（只读挂载从机制上保证）。
- 不迁移、不回填历史记录（见「十、删除旧机制」）。

## 二、概念模型

| 概念 | 定义 |
| --- | --- |
| **Task Agent** | 现有的开发 agent：在隔离 Runtime 中按 instruction 修改代码。 |
| **Validation Agent（judge）** | 独立的第二个 agent：在全新容器中，按 validation prompt 检查 Task Agent 的产出，并调用 verdict 工具提交判定。 |
| **Round（轮次）** | 一次 judge 判定，以及（若失败）它触发的返工 run。第 1 轮 judge 判定的对象是初始开发 run 的产出；第 N (≥2) 轮判定的对象是第 N-1 轮返工 run 的产出。 |
| **Rework Run（返工 run）** | 判定失败后，Task Agent 在同一 Workspace 上的新开发 run，指令 = 原始 instruction + 上一轮 verdict。 |
| **Verdict（判定结论）** | judge 提交的结构化结论：`passed` / `summary` / `unmet[]` / `evidence[]`。生成时冻结，之后只读。 |

**预算**：`maxAttempts`（默认 3）= 一个 validation 循环内允许的 judge 判定次数。judge 判定「不通过」消耗一次；judge 因环境/基础设施原因没能产出判定（容器起不来、judge run 超时后无 verdict、verdict 缺失）**不**消耗判定次数。

## 三、配置模型

### 3.1 类型

`packages/core/src/git.ts` 新增两个原语（仅 4.5 的回放路径使用）：`resetHard({ dir, revision })`、`cleanUntracked({ dir })`。

`packages/core/src/types.ts`：删除 `ValidationStep` / `ValidationConfig.steps`，替换为：

```ts
/** Project/Task 级 validation 配置（v12）。存在即启用。 */
export interface ValidationConfig {
  /** 自然语言验收标准。必填、非空。 */
  prompt: string;
  /** 一个循环内允许的 judge 判定次数（≥1，默认 3）。 */
  maxAttempts?: number;
  /** judge 使用的 model；缺省跟随 Task 的 model。 */
  modelId?: ID;
  /** judge run 的超时；缺省跟随 Task / policy 的既有解析链。 */
  timeoutMs?: number;
}
```

- **存在即启用**：去掉 `enabled` 字段——「启用」由 prompt 的存在表达。
- **prompt 为空即配置错误**：API 边界（创建 / 更新 Project、创建 Task）校验 `validation.prompt` 非空，否则 `config-invalid`（400）。**未传 `validation` = 未配置 = 跳过**；UI 上空 textarea 表示不传该字段，不是传空 prompt。
- **Task 级整体替换 Project 级**：沿用既有规则（skills / mcpServers 同款），不逐字段合并。
- `validationSecretIds` 保留（Project `execution.validationSecretIds` / Task 请求体），语义不变：judge run 的环境里允许出现的 build/test 密钥；`scope: "git"` 的密钥依旧被拒绝。

### 3.2 配置入口

| 入口 | 变更 |
| --- | --- |
| Web · 创建项目 | Validation 输入从「一行一条命令」改为自然语言 prompt textarea；空 = 不启用。可附 maxAttempts 数字输入（默认 3）。 |
| Web · 项目内建 Task / 侧边栏建 Task | Validation override 同样改为 prompt；留空 = 继承（Task 不声明）。placeholder 显示 Project 继承的 prompt（现有先例保留）。 |
| REST | `POST/PUT /api/projects`、`POST /api/projects/:id/tasks` 接受新形态 `validation`。 |
| CLI | `af projects add / update` 增加 `--validation-prompt`、`--validation-max-attempts`（可选；补上 docs/validation.md 承认的缺口）。 |

## 四、执行模型

### 4.1 Validation Agent 是一次普通的 Run

judge 不是新的执行器，而是**复用现有 Run 机制的一次运行**：`RunService.createRunForTask` + `executeRun`，因此容器生命周期、harness、provisioning、usage 记账、事件、取消、超时全部白拿。新增标记：

```ts
/** Run 的用途（v12）。缺省 = 开发 run。 */
purpose?: "development" | "validation" | "rework";
/** validation / rework run 所属轮次（1-based）。 */
round?: number;
```

judge run 的规格：

| 维度 | 取值 |
| --- | --- |
| Runtime | Task 的 runtime（同一镜像、同一隔离要求；不再有 validation 专属的隔离门禁——validation 的信任级别 = agent 的信任级别，见「九」）。 |
| 容器 | 每轮一个**全新**容器（现有 `ephemeral` 默认即如此）。 |
| 工作区挂载 | **只读**（run 级 policy `filesystem.readOnly = true`）。 |
| 环境 | `task.env` + `validationSecretIds` 解析出的密钥（scope 校验）；**不含** `task.secretIds`；**没有** Git Source Credential（Run 路径本来就拿不到）。 |
| 网络 | 与 agent 容器**同一 resolver 的同一份 policy**（`policy.ts`），网络权限绝不大于 agent。 |
| 模型 | `validation.modelId ?? task.modelId`（provider 可用性 preflight 照走）。 |
| 超时 | `validation.timeoutMs ?? task.timeoutMs ?? policy ?? 默认`。 |
| Skills / MCP | **不注入** Project 的 skills / mcpServers；只 provision verdict 工具脚本与输出目录（见「五」）。 |
| 输出通道 | 一个 **rw** 挂载的 verdict 输出目录（位于 `dataDir` 下、Workspace 之外），其余 provisioning 挂载保持只读。 |

实现注意：`commonRunArgs` 里 `extraMounts` 一律 `:ro`，verdict 输出目录不能走 extraMounts，需要与 `nativeStateMount` 同级的专用 rw 挂载接线（`writableMounts`，runtime → harness → docker backend 全链路透传）；provisioning 对 `validationJudge` 的 run 写入工具脚本、生成工具（`:ro`）与输出目录（`:rw`）两个挂载（唯一一处内置特例，集中在该文件）。

judge run 的 **container lifecycle 强制 `ephemeral`**：keep-alive 的 Task 会通过 lease manager 把开发 agent 的容器（工作区 `:rw`）交给 judge，只读保证会失效。judge 永远一个全新容器、结束即毁。

### 4.2 judge prompt 的组成（生成时冻结）

judge run 的 `inputInstruction` 由以下部分组成（组成逻辑一处实现；run 记录里的 `inputInstruction` 即事实）：

1. 角色与任务：判定当前工作区是否满足验收标准；**不得修改仓库、不得 commit**——工作区只读挂载，且已固定为完工 commit（给出 `pinnedCommitSha`），任何写入都会被平台检测并回放掉，白费力气。
2. 原始 Task instruction（判定的对象是「这个任务有没有被完成」）。
3. validation prompt（用户的自然语言验收标准）。
4. 工作方式：`/workspace` 只读；需要构建 / 测试时把工作区复制到可写目录（如 `cp -a /workspace /tmp/ws`）再跑；给出 `task.baseCommitSha` 与 `pinnedCommitSha`，提示可在副本里用 `git diff <base>..<pin>` 查看本次改动。
5. 判定纪律：结论必须基于**实际执行过的命令与输出**；通过/不通过都要给证据。
6. 提交方式：`node <tool 路径> --passed|--failed --summary ... --unmet ... --evidence ...`（见 5.1）；若工具不可用，直接把同 schema 的 JSON 写到指定文件路径（兜底，见 5.3）。

**不给 judge 看 Task Agent 的对话记录**（保持独立性，避免锚定）。

### 4.3 Rework Run 的规格

- 由循环自动创建（不是用户触发的 retry）：`purpose: "rework"`，`round` = 新轮次；同一 Workspace；`continuity: "new"`（D1）。
- 指令 = 原始 Task instruction + 上一轮 verdict 的结论部分。**只注入结论，不注入 validation prompt**：

```text
<原始 instruction>

---
上一轮开发经验证未通过（第 N/3 轮判定）。以下是验证结论，请针对性地修改：

<verdict.summary>

未满足的要求：
- <unmet 条目…>

验证证据（验证 Agent 实际执行的命令与观察结果）：
- <evidence 条目…>
```

- 环境 / skills / MCP / 密钥 = 正常开发 run（`task.env` + `task.secretIds` + Project skills/MCP），与初始 run 一致。
- 返工 run 走与初始 run 相同的「runtime preparing + provisioning + agent 执行」路径（不含 source preparation）；它的 agent 事件写自己的 run shard。
- 返工 run 失败（agent-failed / timeout / cancelled / runtime-*）→ **立即终止整个 Task**，不再进入下一轮判定（已定决策 4；stage 归类见 D5）。

### 4.4 生命周期结构

`supervisor.ts` 的 `lifecycle()` 改为：

```text
workspace preparing
[full] source preparing
runtime preparing + provisioning（round 1 的 agent run）
[full] agent run（round 1）
—— validation 循环（validation 未配置则整段跳过）——
  round = 1..maxAttempts：
    pin：开发 run 完工 → commit（add -A + commit）→ pinnedCommitSha
    judge run（全新容器，工作区只读挂载）→ verdict
    漂移检测：judge 结束后指纹 ≠ pin → 事件 + reset --hard + clean -fd 回放到 pin
    passed           → 退出循环 → finalization
    round < max      → rework run（携带 verdict）→ 下一轮
    round == max     → 终止：validation-failed（attempts = maxAttempts）
—— 循环结束 ——
git finalization → publish（不变）
```

- `mode === "post-agent"`（Retry Validation）：跳过 source / agent run，直接进入**循环**（预算重置）。
- `mode === "full"` 的初始 agent run 失败语义不变（agent-failed 等），不进入 validation 循环。
- 循环内每步前后检查取消（abort），取消永远优先。
- 每个 judge / rework run 都创建自己的 Run 记录，Task 的 `execution.agent.runId` **不被** judge run 覆盖；judge run 通过 round 记录引用。

### 4.5 完工 Pin 与工作区回放（外层硬约束）

Prompt 约束是软的；本节是机制约束，保证「Validation Agent 不能提交代码」不依赖 judge 的自觉：

**定义 · 完工 Pin**：每次开发 run（初始或返工）成功结束后、进入判定之前，supervisor 把工作区固定为一个 commit：

1. `git add -A` + `git commit`（消息用既有 `commitMessage` 模板，附注 `af-pin: <runId>`），得到 `pinnedCommitSha`；工作区已 clean 则 pin = 当前 HEAD，不产生新 commit。
2. 记录 `pinnedRevision = { commitSha, runId, round, at }` 到 validation 状态（生成时冻结）。
3. 这一步**只在配置了 validation 时执行**；未配置 validation 的 Task 保持现状（finalization 时才 autoCommit）。

对既有模型的说明：当前 autoCommit 发生在 finalization；启用 validation 后提交时机**提前**到每个开发 run 完工时（判定必须有一个确定的 revision 作为对象，且回放必须有 commit 可回放）。finalization 随之不再产生新 commit——工作区在 pin 时已干净。`autoCommit: false` 的组合见 D6。

**校验 · 判定结束后的漂移检测**：每次 judge run 结束后（无论判定结果、也无论 judge 是否异常退出），supervisor 对工作区做与 `assertWorkspaceNotDiverged` 同一套的指纹比对（HEAD + branch + porcelain status）：

- **仍在 pin 上**（指纹一致）→ 继续，无额外动作。
- **漂移**（HEAD 变了 / 有脏改动 / 有 untracked / 换分支）→ 说明 judge（或其拉起的工具）改了工作区：
  1. 发出**响亮的事件** `validation.workspace.replayed`，数据含 `pinnedCommitSha`、`observedHead`、`driftedPaths`（前 N 个）、`judgeRunId`；
  2. **回放到 pin**：`git reset --hard <pinnedCommitSha>` + `git clean -fd`（清 untracked），把工作区恢复到判定对象的确切状态；
  3. 记录 `validation.drift = { detected: true, observedHead, replayedAt }`；
  4. 本轮判定**照常生效**（判定的对象本来就是 pin，不是 judge 改过的树；verdict 有效）。

**回放的边界**：只回放到**本次循环自己的 pin**。返工 run 结束后会创建**新的 pin**（round ≥ 2 的判定对象是返工 run 的 pin），旧 pin 只是历史记录。`git reset --hard` 与 `git clean -fd` 是 GitOps 新增的两个原语（现有接口没有），只允许在本节的回放路径调用，且只允许以 `pinnedCommitSha` 为参数——不允许 reset 到任意 ref。

**实现修正（落地时定案）**：`git reset --hard` 只移动当前所在分支，**不会切回 task 分支**——judge 换到自己的分支后，仅靠 reset + clean 无法满足「HEAD、branch、porcelain 全部回到 pin 状态」（§11.2 的要求）。回放因此在检测到换分支时先 `git checkout <task.workingBranch>` 再 `reset --hard <pin>`（此时工作树已 clean，checkout 不会冲突）；事件与 drift 记录语义不变。落地时还发现 `gitFor()` 绑定用的 `GIT_OPS_METHODS` 列表漏了 `resetHard` / `cleanUntracked` 两个新原语——`v12.validationPin.test.ts` 的漂移用例把它暴露了出来。

**为什么只读挂载之外还要回放**：只读挂载（4.1）挡住的是 judge 容器里的常规写入；回放兜住的是所有穿透路径——judge 通过只读挂载之外的通道（原生会话状态、MCP、未来新增的挂载）留下的痕迹，以及只读挂载接线本身出 bug 的极端情况。两层都做，机制上不存在「judge 的提交进入最终产物」的路径。

**与 frozen revision 的关系**：`execution.frozenRevision`（finalization 冻结、publish 只推它）语义不变，但它现在是**判定通过之后**才写入的；pin 是判定**之前**的锚点。两个概念分开记录、分开命名，UI 都要能看见（pin 在每个 round 里，frozen 在 publish 区块）。

## 五、Verdict 契约

### 5.1 工具

**实现修正（落地时定案）**：原计划的内置 MCP server 不可行——`AGENTFABRIC_MCP_CONFIG` 目前只由 provisioning 生成，没有任何 harness adapter 消费它（README 明说「未逐 harness 写入各自的私有配置格式」）。改成一个**零依赖的 Node 脚本**，由 provisioning 写入 run 的 provisioning 目录，judge 直接 `node <path>` 调用——judge 本来就必须能跑构建/测试命令，这是所有 harness 都必然具备的通道。

参数（严格校验，非法调用不落盘、退出码非 0 并打印原因，judge 可据此改正后重试）：

```jsonc
{
  "passed": true,
  "summary": "1-3 句话的结论",
  "unmet": [],            // passed=false 时必填且非空：未满足的要求条目
  "evidence": [           // 必填且非空：「命令 → 观察结果」条目
    "npm test → 12 passing, 0 failing",
    "go build ./... → exit 0"
  ]
}
```

调用形式：`node <tool> --passed|--failed --summary "..." [--unmet "..."]... --evidence "..."...`。合法 payload 写入输出目录的 `verdict.json`（覆盖）并追加到 `verdict-calls.jsonl`（留痕）；退出码 0 成功 / 2 非法 payload / 1 I/O 失败。要求容器镜像里有 `node`（大多数 harness 镜像天然满足）；工具起不来时走 5.3 的文件兜底。

### 5.2 冻结与记录

judge run 结束后，supervisor **在生成那一刻**读取 verdict 文件、校验 schema，并冻结到：

- Task 记录的 round 条目（见「六」）；
- 事件 `validation.verdict`；
- artifact `validation-verdict.json`（含 round、judgeRunId、完整 verdict；原 `validation-report.txt` 随旧机制删除）。

读取路径（UI / API）原样返回记录，不重新解析、不重算（AGENTS.md 核心规则）。

### 5.3 缺失与非法

- judge run 正常结束但输出目录里没有 `verdict.json`，或文件不是合法 schema → `validation-verdict-missing`（502，D3）：**判定没有发生**，不消耗预算，可自动/手动重试。
- 文件兜底路径：judge prompt 明确给出 `verdict.json` 的绝对路径与 schema，工具不可用时允许直接写文件；两条路径产出同一契约。

## 六、返工循环、状态与记录

### 6.1 状态类型

```ts
export interface ValidationVerdict {
  passed: boolean;
  summary: string;
  unmet: string[];
  evidence: string[];
  round: number;
  judgeRunId: ID;
  at: string;              // 冻结时刻
}

export interface ValidationRound {
  round: number;
  /** 本轮判定的对象（round 1 = 初始开发 run；round ≥2 = 上一轮 rework run）。 */
  agentRunId?: ID;
  /** 本轮由哪次返工产出（round ≥2）。 */
  reworkRunId?: ID;
  /** 本轮判定对象的完工 pin（4.5）：判定与回放都锚定这个 commit。 */
  pinnedRevision?: PinnedRevision;
  /** judge 结束后检测到的工作区漂移与回放记录（4.5）。 */
  drift?: { detected: true; observedHead?: string; driftedPaths?: string[]; replayedAt: string };
  judgeRunId?: ID;
  verdict?: ValidationVerdict;
  status: "judging" | "passed" | "failed" | "interrupted";
  startedAt?: string;
  endedAt?: string;
  error?: string;
  errorCode?: string;
}

export interface PinnedRevision {
  commitSha: string;
  /** 产生这个 pin 的开发 run。 */
  runId: ID;
  round: number;
  at: string;
}

export interface TaskValidationState {
  status: "pending" | "skipped" | "running" | "passed" | "failed" | "timeout" | "interrupted";
  /** 当前循环内已产出的 judge 判定次数（手动重试 / post-agent 生命周期重新计数）。 */
  attempts: number;
  /** 完整轮次历史（跨重试追加，不重算）。 */
  rounds?: ValidationRound[];
  /** 最后一个冻结的 verdict（便捷读取）。 */
  verdict?: ValidationVerdict;
  error?: string;
  errorCode?: string;
  startedAt?: string;
  endedAt?: string;
}
```

删除 `ValidationStepResult`、`ValidationExecutionInfo`（judge run 自己的记录已带 runtime / image 证据，不需要第二份）。

### 6.2 阶段与单调性

- `RunPhase` 新增 `"validation.reworking"`（返工 run 执行期间）；`STAGE_BY_PHASE` 映射到 `validation`。
- **阶段单调性修订**：现有规则「completed 的阶段不能被改写」在本期必须显式放宽——validation 循环允许 `agent` 阶段 completed → running → completed 的**重入**（返工 run），`stages.agent` 始终反映最近一次开发 run 的结果。这是对 v11 hardening §36 不变量的**有意修订**，注释与 README 必须同步说明；除此之外的单调性不变（validation.completed 依旧不被 publish 失败改写等）。
- `stagePatch` 增加仅循环可走的显式重入路径，不允许其它调用点绕过。

### 6.3 事件

保留 / 新增（`validation.runtime.prepared`、`validation.step`、validation 语义的 `shell.command` 随旧机制删除；judge 自己的 shell 事件由它自己的 run 发出）：

| 事件 | 数据 |
| --- | --- |
| `validation.round.started` | `{ round, maxAttempts, judgeRunId }` |
| `validation.pinned` | `{ round, commitSha, runId }`（4.5 的完工 pin） |
| `validation.verdict` | `{ round, passed, summary, unmet, judgeRunId }` |
| `validation.workspace.replayed` | `{ round, judgeRunId, pinnedCommitSha, observedHead, driftedPaths }`（仅在检测到漂移时发出，响亮事件） |
| `validation.rework.started` | `{ round, reworkRunId }` |
| `validation.passed` | `{ attempts, rounds }` |
| `validation.failed` | `{ attempts, maxAttempts, exhausted: true, verdict }` |
| `validation.skipped` | `{}`（未配置时；补上现有静默跳过的可观察性） |

judge run / rework run 自身的 `run.phase` / `shell.*` / `usage.updated` 等事件写各自 run 的 shard。

### 6.4 重试与恢复

- **手动 Retry Validation**（Web 按钮 / `af tasks retry-validation` / `POST /api/tasks/:id/retry-validation`）：要求已配置 validation，否则 `task-state-invalid`（400）；以 `post-agent` 生命周期进入循环，**预算重置**（attempts 归零，rounds 历史保留）。
- **Retry Agent Run**：现有语义不变（新 run、同 workspace、full 生命周期）；validation 循环随之重新开始（新循环 = 新预算）。
- **崩溃恢复表更新**（README 与 supervisor 注释同步）：
  - 崩在 judge run（`validation.running`）→ validation interrupted → **Retry Validation** 重跑该轮 judge（该轮未产出判定，不消耗预算）。
  - 崩在返工 run（`validation.reworking`）→ validation interrupted → **Retry Validation**：对当前（可能只改了一半的）工作区重新 judge；若判定不通过，循环自然继续返工（预算未被消耗）。半成品被 judge 判负并再次返工是**可接受的恢复路径**，不做「先补跑返工」的复杂化。
  - 崩溃发生在 pin 已写入、judge 未开始的窗口：恢复时以记录的 `pinnedRevision` 为锚，先做一次漂移检测（重启期间可能有残留写入），需要则回放，再起 judge。
  - 崩在 finalization / publish 的既有行为不变。

### 6.5 自动重试

`autoRetry` 的瞬态 allowlist 增加 `validation-verdict-missing`；`validation-runtime-failed` / `validation-runtime-unavailable` 保持。判定不通过（`validation-failed`）与 judge 超时（`validation-timeout`）**不**自动重试。自动重试走既有 Retry Validation 操作（即重置预算的那条路径，语义自洽：判定没发生，重来一次）。

### 6.6 取消

- 取消落在 judge run / 返工 run 上：终止在飞 run，validation 记 `interrupted`（复用现有取消路径与事件）。
- 循环在各轮之间检查 `assertNotCancelled`，被取消的 Task 不会被循环唤醒。

## 九、安全与信任边界

1. **judge 不得写 Workspace**：两层机制保证（不是提示词约定）——(a) 只读挂载：judge 容器里 `/workspace` 是 `:ro`；(b) 完工 pin + 回放（4.5）：判定对象固定为 pinned commit，judge 结束后检测漂移并 `reset --hard <pin>` + `clean -fd` 回放。判定在 pin 时工作区已提交，finalization 不再产生新 commit——judge 的任何写入都没有进入最终产物的路径。judge 需要构建时在容器内复制副本。2. **judge 不得拥有超过 agent 的权限**：同一 network policy resolver；无 Git Source Credential；环境只含 `task.env` + `validationSecretIds`，**不含** `task.secretIds`；无 Docker socket；除只读工作区与 verdict 输出目录外无宿主路径。
3. **信任边界变化（有意）**：旧模型中 validation 是独立执行路径，因此有独立的隔离门禁（且与 `allowHostExecution` 存在已记录的耦合不一致）。新模型中 judge 与 agent 走同一 Run 路径、同一 runtime 要求——**validation 的信任级别等于 agent 的信任级别**。`docs/validation.md`「边界」一节与 README 的相关表述必须改写，不留旧说法。
4. **verdict 是判定者的输出**：judge 可能被仓库内容影响而给出错误结论（LLM 固有风险）。缓解：schema 强制 evidence 非空、verdict 全文可查、成本可控（最多 3 轮）。不做机器验证 evidence 真实性——那是另一个课题。
5. **verdict 输出目录在 Workspace 之外**（`dataDir` 下），judge 对它可写但读方是 supervisor；输出目录随 run 的 provisioning 清理。

## 十三、验收标准（Done 的定义）

1. 一个配置了 validation prompt 的 Project Task：agent 完成 → judge 在全新容器判定 → 通过则 finalization / publish；不通过则自动返工并重判；3 次判定失败后 Task 以 `validation-failed` 终止，记录含 3 个 round 的完整 verdict。
2. 未配置 validation 的 Project Task：跳过判定，行为与今天一致。
3. verdict 是机器可解析的确定性产物；judge 未提交 / 提交非法 → 502 类失败、可重试、不消耗预算。
4. 手动 retry-validation 重置预算并重跑循环；rounds 历史保留。
5. judge 对 Workspace 只读；无 git credential；网络权限不高于 agent。
6. **judge 无法把代码写进最终产物**：判定期间工作区固定在完工 pin 上；judge 造成的任何 commit / 改动（包括只读挂载被穿透的极端情况）在判定结束后被检测、响亮记录并回放清除，finalization 提交的只能是 pin 之后判定通过的状态。
7. 旧 steps 机制与相关代码、事件、Web 表单、文档全部移除，无兼容分支；全仓库 typecheck / test 通过。
