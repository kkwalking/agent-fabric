# AgentFabric：Project + Isolated Runtime Task Lifecycle

请基于当前 AgentFabric 项目的既有架构和代码实现以下功能。

本次工作的核心目标，是完善 AgentFabric 除 Handoff 之外的另一条核心能力：

> **围绕一个代码项目，在隔离 Runtime（当前主要为 Docker）中完成从源码准备、Agent 开发、任务状态管理，到最终 Git 分支推送的完整 Coding Task 生命周期。**

请首先阅读当前代码、README、领域模型、Task / Run / Workspace / Runtime / Harness / Secret / Handoff 等现有实现，在最大程度保持现有架构一致性的基础上进行设计和开发。

不要为了本需求大规模重写已经稳定的 Handoff 功能。本次重点是补齐 Project-based task execution lifecycle，并重新明确 Workspace 在整个系统中的职责。

---

# 一、核心目标

系统最终应支持以下完整用户流程：

1. 用户配置一个 Source Credential。
2. 用户创建一个 Project。
3. Project 绑定一个远程 Git Repository Source。
4. 用户基于 Project 创建一个 Task。
5. 创建 Task 时选择：
   - 基础分支 / base ref；
   - Task 工作分支；
   - Runtime / Harness / Model 等执行配置；
   - Task instruction。
6. 系统创建该 Task 独占的 Workspace。
7. 系统通过受控方式获取 Git Credential。
8. 系统拉取 Project 对应的远程源码。
9. 根据指定 base ref 创建 Task branch。
10. 拉起隔离的 Runtime Container。
11. 将 Workspace 挂载到 Runtime。
12. 配置 Agent 所需 Skills / MCP / Harness / Runtime 环境。
13. Agent 在隔离 Runtime 中完成编码任务。
14. 系统持续监控 Agent / Runtime 生命周期。
15. Agent 执行结束后，系统进入 Finalization。
16. 对代码状态进行检查，并根据策略产生最终 Git commit。
17. 将 Task branch 推送至 Project 对应的远程 Repository。
18. 记录最终 commit SHA、remote branch、执行结果等信息。
19. Runtime Container 可以销毁。
20. Workspace 保持存在，以便：
    - 查看结果；
    - 后续 Run；
    - Handoff；
    - Debug；
    - Retry publish。

最终需要形成这样的核心抽象：

> **Project defines the codebase.  
> Task defines the intent.  
> Workspace holds the work.  
> Run executes the agent.  
> Runtime is disposable.  
> Supervisor owns the execution lifecycle.**

---

# 二、核心领域模型

本次开发需要明确以下领域模型及其职责边界。

不要简单将所有信息继续塞入 Workspace 或 Run。

---

## 2.1 Project

Project 是一个长期存在的顶层业务资源。

它表示：

> 一个用户希望 AgentFabric 持续进行开发工作的代码项目。

Project 至少需要包含以下概念：

- 唯一标识；
- 名称；
- Source；
- 默认执行相关配置；
- 可选的 Skills 配置；
- 可选的 MCP 配置；
- 可选的 Runtime / Harness / Model 默认值；
- Git publish 相关默认策略；
- 创建 / 更新时间等必要元数据。

Project 应该是 Task 的上游资源。

关系：

```text
Project
  └── Task
       └── Workspace
            └── Run
```

一个 Project 可以拥有多个 Task。

---

# 三、Project Source

当前阶段，一个 Project 必须拥有一个 primary source。

目前只要求实现：

```text
Source Type = Git
```

Git Source 至少需要支持：

- HTTPS Repository；
- SSH Repository；
- GitHub；
- GitLab；
- Gitee；
- Generic Git Server；
- Public Repository；
- Private Repository。

Source 应包含类似以下业务信息：

- Remote URL；
- Default Branch；
- 可选的 Source Credential Reference；
- 必要的 provider / type 信息。

当前版本不要求支持：

- 一个 Project 多 Repository；
- monorepo 内多个独立 Source；
- Repository mirror；
- submodule 独立管理。

但是领域模型不要设计成明显阻碍未来扩展这些能力。

当前阶段建议：

> Source 作为 Project 的必备组成部分即可，不需要为了形式上的抽象单独构造复杂的顶层 Source 生命周期。

---

# 四、Source Credential

需要新增独立于 Project 的 Source Credential 概念。

不要直接使用 `SourceToken` 作为最终抽象，因为 Git Authentication 不只有 Token。

Source Credential 属于 Settings / Global Configuration 层，而不是 Project 私有数据。

例如：

```text
Source Credentials

- Personal GitHub
- Company GitLab
- Gitee
- Internal Git SSH
```

Project 只保存 Credential Reference。

---

## 4.1 Credential 类型

至少考虑：

- HTTPS Token；
- SSH Private Key。

设计上应允许未来支持：

- GitHub App；
- GitLab Access Token；
- Deploy Key；
- Short-lived Credential；
- OAuth Credential。

---

## 4.2 Credential 与 Secret

敏感值必须继续使用 AgentFabric 已有的 Secret 系统。

Source Credential 负责描述：

- Credential 类型；
- 适用 Host；
- username 等非敏感元数据；
- Secret Reference。

真正的：

- token；
- private key；
- passphrase；

不能直接作为 Project 或 SourceCredential 的普通明文配置长期保存。

---

## 4.3 Public Repository

公开仓库必须允许：

```text
credential = none
```

用户创建 Project 时不应被强制要求提供 Credential。

---

# 五、Workspace 重新定位

本次需求中需要明确 Workspace 的职责。

Workspace 不再承担“Project Definition”的职责。

Workspace 的核心定义调整为：

> **Task-specific mutable working copy。**

即：

```text
Project
= 我正在开发哪个项目

Task
= 我要完成什么需求

Workspace
= 该 Task 当前实际代码状态存放在哪里

Runtime
= Agent 此刻在哪里执行
```

---

## 5.1 Project Task 与 Workspace

对于 Project-based Task：

```text
1 Task = 1 Managed Workspace
```

默认情况下，一个 Task 应拥有自己的独立 Workspace。

不同 Task 即使来自同一个 Project，也不能共享相同 working tree。

例如：

```text
Project: agent-fabric

Task A
  branch: af/project-model
  workspace: workspace-A

Task B
  branch: af/runtime-supervisor
  workspace: workspace-B
```

二者必须隔离。

---

## 5.2 Workspace 与 Run

一个 Task 可以执行多个 Run。

因此：

```text
1 Task = 1 Workspace
1 Task = N Runs
```

例如：

```text
Task
 └── Workspace
      ├── Run 1
      ├── Run 2
      └── Run 3
```

Run 可以因为：

- Runtime 重启；
- Handoff；
- Harness 切换；
- Agent 失败；
- 用户重新执行；

而重新创建。

但 Workspace 中的代码修改应持续存在。

---

## 5.3 Workspace 生命周期

需要明确：

```text
Runtime Container 生命周期
!=
Workspace 生命周期
```

Runtime 可以是 disposable。

Workspace 应 durable。

Runtime 销毁不能导致 Task 工作内容丢失。

---

## 5.4 Existing / External Workspace

如果当前系统已经支持：

- Local Workspace；
- Import Directory；
- Existing Git Workspace；
- Attach Existing Workspace；

不要强制删除这些能力。

可以将 Workspace 在概念上区分为：

```text
Managed Workspace
External Workspace
```

Managed Workspace 由：

```text
Project + Task
```

自动产生。

External Workspace 用于高级使用场景以及兼容已有功能。

---

# 六、Task 模型增强

Project-based Task 至少应具备：

- project reference；
- workspace reference；
- instruction；
- base ref；
- working branch；
- branch creation mode；
- execution config；
- publish result；
- lifecycle status。

---

# 七、Base Ref 与 Working Branch 必须分离

Task 不应只有一个 `branch` 字段。

必须明确区分：

```text
baseRef
workingBranch
```

例如：

```text
baseRef = main

workingBranch =
af/add-project-model
```

启动 Task 时，应从 baseRef 解析真实 Git revision。

系统需要记录本次 Task 启动时真正基于的：

```text
baseCommitSha
```

原因是：

```text
main
```

会移动，而 commit SHA 不会。

需要能够明确回答：

> 这个 Task 最初是基于哪个具体 commit 开始开发的？

---

# 八、Task Branch

用户创建 Task 时：

工作分支名称可以：

1. 用户自定义；
2. 系统自动生成。

系统自动生成时，应采用稳定且可识别的命名方式，例如：

```text
af/<task-id>-<slug>
```

具体格式可以根据现有系统 conventions 调整。

---

## 8.1 Branch Collision

系统必须处理：

- branch 已存在；
- branch 被另一个 active Task 使用；
- remote branch 已存在；
- branch 名非法。

当前版本建议默认：

> 新 Task 创建新的 working branch。

不要默默覆盖已有远程分支。

如果未来需要：

```text
continue existing branch
```

应作为明确的 branch mode，而不是隐式行为。

---

# 九、完整 Task Execution Lifecycle

需要实现完整 Task lifecycle。

至少覆盖以下阶段：

```text
Task Created

→ Workspace Preparing

→ Source Preparing

→ Runtime Preparing

→ Agent Running

→ Validation

→ Git Finalization

→ Publishing

→ Cleanup

→ Completed
```

失败时进入对应失败状态。

---

# 十、Workspace Preparing

系统创建 Task 后：

如果是 Managed Workspace，需要为该 Task 创建独立的 Workspace。

Workspace 必须：

- 独属于当前 Task；
- durable；
- 可以跨 Run 复用；
- 可以被 Runtime 挂载；
- Runtime 删除后仍然存在。

---

# 十一、Source Preparing

系统在 Agent 执行之前负责完成 Git Source 初始化。

需要覆盖：

- Repository clone；
- Repository fetch；
- credential handling；
- default/base branch resolve；
- base revision resolve；
- working branch creation；
- checkout；
- base commit recording。

最终 Runtime 启动前，Workspace 应已经处于正确的 Task branch。

---

# 十二、Credential Security Boundary

这是本需求的重要安全要求。

Git Credential 不应该作为长期环境变量、命令参数或 Repository URL 暴露给 Agent。

禁止形成类似：

```text
https://TOKEN@github.com/org/repo.git
```

的持久 Remote URL。

Git Credential 不应写入：

- `.git/config`；
- shell history；
- event log；
- application log；
- task metadata；
- runtime output；
- error message。

---

## 12.1 Credential 使用

Credential 应只在必要 Git operation 执行时短暂存在。

HTTPS 可以采用安全的临时认证方式。

SSH 需要正确处理：

- private key；
- known_hosts；
- optional passphrase；
- temporary secret mounting。

具体实现方式由现有技术架构决定。

关键要求是：

> Agent 不需要、也不应该直接获得 Repository write credential。

---

# 十三、Execution Supervisor

需要增加一个明确的 Execution Supervisor 概念。

Supervisor 是整个 Task / Run 生命周期的执行负责人。

但不要将一个拥有所有权限的大型 Supervisor 直接放进 Agent Sandbox，并将其和 Agent 放在同一个 trust domain。

整体安全边界建议为：

```text
AgentFabric Control Plane

        ↓

Execution Supervisor

        ↓

Agent Runtime Container
```

---

# 十四、Supervisor 职责

Supervisor 至少需要负责以下业务能力：

### Workspace lifecycle

- prepare workspace；
- lock workspace；
- attach workspace；
- preserve workspace；
- cleanup temporary resources。

### Source lifecycle

- clone；
- fetch；
- checkout；
- branch；
- revision resolve。

### Credential lifecycle

- resolve credentials；
- temporary credential injection；
- revoke / cleanup credentials；
- prevent secret leakage。

### Runtime lifecycle

- create runtime；
- monitor runtime；
- timeout；
- stop；
- cancel；
- destroy runtime。

### Runtime provisioning

- Harness config；
- Skill provisioning；
- MCP provisioning；
- Agent config；
- Model config；
- environment；
- native state mount；
- workspace mount。

### Execution monitoring

- process exit；
- heartbeat；
- stdout / stderr；
- structured event；
- cancellation；
- timeout。

### Finalization

- inspect repository state；
- validate result；
- commit；
- push；
- record final revision。

---

# 十五、Runtime Shim

Runtime Container 内建议只存在一个权限受限的 Runtime Shim / Runner。

其主要职责是：

- 启动 Harness；
- signal forwarding；
- heartbeat；
- stdout/stderr transport；
- structured event forwarding；
- exit code reporting；
- process lifecycle。

它不应该拥有 Source Credential。

它不应该承担 Project-level Git publish 权限。

Agent 可以拥有 Workspace 内正常开发需要的权限，但不能因此自然获得远程 Repository credential。

---

# 十六、Agent 与 Git Publish 的职责分离

不要依赖 Prompt 告诉 Agent：

> 开发完以后记得 commit 和 push。

最终 Git publish 必须由平台控制。

Agent 的主要职责：

```text
coding
analysis
testing
tool execution
```

Platform / Supervisor 的职责：

```text
source preparation
branch ownership
commit policy
publish
credential
cleanup
```

---

# 十七、Git Finalization

Agent 成功结束后，应进入 Git Finalization。

系统至少检查：

- 当前 branch；
- working tree status；
- tracked changes；
- untracked files；
- commits produced by Agent；
- HEAD revision。

如果存在未提交修改，根据 Project / Task policy 决定是否自动 commit。

默认应支持：

> 即使 Agent 没有主动执行 git commit，Task 仍然可以最终将开发成果正确发布到远程 working branch。

---

## 17.1 Agent-created Commit

如果 Agent 已经产生 commit：

系统不应无理由破坏或 squash 用户已有 commit。

如果仍存在 dirty changes，可以根据 finalization policy 再补充最终 commit。

---

## 17.2 Finalization Result

至少应记录：

- base commit SHA；
- final commit SHA；
- working branch；
- remote branch；
- pushed time；
- publish result。

---

# 十八、Git Push

Git Push 必须是 Supervisor / Platform capability。

不要简单设计为一个 Agent 可任意调用的：

```text
git.push MCP tool
```

Agent 不应该自然获得执行以下操作的能力：

- push arbitrary branch；
- force push；
- push tags；
- 修改 remote；
- push 到其他 repository；
- 获取 credential。

系统应限定：

> 本 Task 只能发布到它拥有的 working branch。

---

# 十九、Agent Completion Signal

如果现有 Harness / MCP 模型适合，可以提供类似：

```text
task.complete
```

的 completion signal。

其作用仅仅是通知平台：

> Agent 认为任务开发已经结束，可以进入 validation / finalization。

它不负责 Git Push。

如果当前 Harness 的 process exit 已经能够可靠表达 Agent completion，本期也可以优先使用现有机制。

不要为了增加 MCP Tool 而增加不必要复杂度。

---

# 二十、Validation

Agent 完成代码开发后，Project 可以定义 Validation。

例如：

```text
typecheck
test
lint
build
```

Validation 可以是：

- Project 默认；
- Task override。

Validation 失败时：

需要清楚地区分：

```text
agent execution failure
validation failure
publish failure
```

不能全部表现为普通的 `Task Failed`。

---

# 二十一、Run Status 与 Run Phase

如果现有系统已经有：

```text
Pending
Starting
Running
Completed
Failed
Cancelled
Timeout
```

等 Run Status，可以继续保留作为 coarse-grained status。

需要增加更细粒度 Phase / Stage 概念，至少能够表达：

```text
workspace.preparing

source.fetching
source.checkout

runtime.preparing

agent.running

validation.running

git.finalizing
git.pushing

cleanup
```

---

# 二十二、错误模型

需要设计清晰的 domain error。

至少应能够区分：

### Source

```text
source-auth-failed
source-not-found
source-network-failed
base-ref-not-found
branch-invalid
branch-conflict
```

### Workspace

```text
workspace-create-failed
workspace-locked
workspace-invalid
```

### Runtime

```text
runtime-create-failed
runtime-start-failed
runtime-lost
runtime-timeout
```

### Agent

```text
agent-start-failed
agent-failed
agent-timeout
agent-cancelled
```

### Validation

```text
validation-failed
```

### Git Finalization

```text
git-state-invalid
git-commit-failed
```

### Publishing

```text
git-push-failed
git-push-auth-failed
git-push-rejected
remote-branch-conflict
```

具体命名遵循当前项目 convention 即可。

---

# 二十三、Development Completed 与 Publish Failed 必须分开

重点场景：

```text
Agent 已经完成开发
↓
代码已经在 Workspace
↓
Commit 已经生成
↓
Git push 因网络 / credential 问题失败
```

这种情况下不能重新执行 Agent。

系统应该能够表达：

```text
Development = Completed
Publishing = Failed
```

并允许执行：

```text
Retry Publish
```

Retry Publish 不应该再次调用模型或者重新运行 Agent。

---

# 二十四、Project Execution Configuration

Project 应逐渐成为 execution configuration 的默认继承根。

配置继承关系建议保持：

```text
Global Settings
      ↓
Project
      ↓
Task
      ↓
Run
```

至少为以下配置预留清晰的继承模型：

- Runtime；
- Harness；
- Model；
- Skills；
- MCP Servers；
- Environment；
- Secret references；
- Timeout；
- Resource Limit；
- Validation；
- Git publish；
- Network Policy。

具体字段和 override 机制需要根据现有代码风格设计。

---

# 二十五、Skill Provisioning

Project 可以配置默认 Skills。

Task / Run 可以在允许的情况下进行 override。

Runtime 启动前，Supervisor 应确保需要的 Skills 已经正确 provision 到 Agent Execution Environment。

Skill provisioning 应：

- 可重复执行；
- 不污染其他 Task；
- 不依赖长期存在的 Container；
- 可以跨 Runtime 重新恢复。

---

# 二十六、MCP Provisioning

Project 可以定义默认 MCP Servers / MCP Tools。

Task / Run 可在策略允许情况下 override。

Runtime 启动前，Supervisor 负责生成最终 MCP Configuration。

需要考虑：

- Secret 注入；
- Scope；
- 权限；
- Runtime isolation；
- configuration cleanup。

不要让 Repository 文件自动获得访问任意敏感 MCP 的权限。

---

# 二十七、Repository Configuration Trust Boundary

未来可能支持：

```text
.agentfabric.yml
```

或者类似 Repository-local config。

即使本期不完整实现，也必须保证领域设计不会混淆：

### Control Plane Configuration

可信配置：

- credentials；
- secrets；
- runtime permissions；
- network policy；
- resource limits；
- publish permissions；
- privileged MCP access。

### Repository Configuration

Repository 内容属于不可信输入。

可以允许定义：

- build hints；
- bootstrap；
- tests；
- project metadata；
- repo-local skill hints。

Repository 配置不能自行申请：

- Production Credential；
- arbitrary Secret；
- elevated Runtime permission；
- arbitrary network access；
- arbitrary Git publish target。

---

# 二十八、Runtime Isolation

本次功能的一个核心目标就是：

> Task 需要在隔离 Runtime 中执行。

至少需要保证：

- Task Runtime 之间互相隔离；
- Workspace 访问有明确边界；
- Secret 不被无关 Task 获取；
- Runtime 可以可靠销毁；
- Runtime 销毁不影响 Workspace；
- Runtime 不能因为 Docker socket 等能力逃逸到 Host；
- Resource limit 可以由现有 Runtime 系统控制。

不要为了方便 Supervisor 而破坏已有 Sandbox 安全边界。

---

# 二十九、Runtime Lifecycle

完整行为至少包含：

```text
create
prepare
start
monitor
stop
cancel
timeout
destroy
```

即使 Runtime 异常：

- crash；
- timeout；
- process exit；
- host restart；

Workspace 也应尽可能保持可恢复状态。

---

# 三十、Handoff Compatibility

当前 Handoff 已经是 AgentFabric 的主要能力之一。

本次开发不能破坏：

- Run handoff；
- Harness handoff；
- Native State；
- Workspace persistence；
- Resume。

需要保持一个重要边界：

```text
Workspace
=
用户代码 / 文件 / working tree state

Native State
=
Harness private state / session state
```

二者不能混在一起。

---

# 三十一、Task Retry

需要明确不同 Retry 的语义。

至少区分：

### Retry Agent Run

重新启动新的 Run，继续当前 Workspace。

### Retry Validation

不重新开发，只重新执行 validation。

### Retry Publish

不重新执行 Agent，只重新 push 当前最终 commit。

不要用一个通用：

```text
Retry Task
```

隐藏所有不同失败类型。

---

# 三十二、Cancellation

用户应该能够取消正在执行的 Task / Run。

取消时：

- Runtime process 应终止；
- Supervisor 进入 cleanup；
- Workspace 保留；
- 当前代码修改不应该默认删除；
- Credential 应及时撤销 / cleanup；
- Task 状态应该准确反映 cancellation。

用户后续应该可以基于相同 Workspace 继续运行新的 Run。

# 三十五、Concurrency

需要考虑同一个 Project 下多个 Task 并行执行：

```text
Project
 ├── Task A
 ├── Task B
 └── Task C
```

三者必须拥有：

- 独立 Workspace；
- 独立 working branch；
- 独立 Runtime；
- 独立 execution state。

不能因为共享 Project 导致 working tree 污染。

---

# 三十六、Workspace Lock

同一个 Workspace 不应被两个不兼容的 active Run 同时写入。

如果未来需要 parallel Agent，可以另行设计。

当前默认：

> 一个 Managed Workspace 同一时刻只有一个 active writer。

需要避免：

```text
Run A
Run B
```

同时修改同一个 working tree 导致不可预测行为。

---

# 三十七、Idempotency 与 Crash Recovery

Supervisor 中存在多个可能被重复执行的生命周期步骤：

```text
prepare workspace
clone
checkout
create branch
start runtime
finalize
commit
push
cleanup
```

这些操作应尽可能设计为：

- 可检测当前状态；
- 可安全重试；
- 避免重复产生破坏性副作用。

特别关注：

- Supervisor 重启；
- API Server 重启；
- Runtime crash；
- Network failure；
- Push 返回超时但实际已经成功。

系统应尽可能通过 Git remote 状态和本地 revision 判断真实执行结果。

# 四十三、验收标准

可以创建一个绑定 Git Remote Repository 的 Project。

Project 可以引用独立配置的 Source Credential。

Public Repository 不需要 Credential。

### AC-4

用户可以基于 Project 创建 Task。

用户可以选择 base ref。

用户可以自定义 working branch，也可以由系统生成。

### AC-11

系统可以启动隔离 Docker Runtime。

### AC-12

Workspace 被正确挂载到 Runtime。

### AC-13

Agent 可以在 Workspace 中正常修改代码。

### AC-14

Runtime 删除后 Workspace 仍然存在。

### AC-15

同一个 Task 可以基于原 Workspace 创建新的 Run。

### AC-16

Agent 无法获得 Git write credential 明文。

### AC-17

Credential 不出现在日志、事件、Remote URL 或错误信息中。

Agent 开发完成后系统能够进入 Validation。

Validation 成功后进入 Git Finalization。

即使 Agent 没有 commit，系统也能根据配置生成最终 commit。

### AC-21

系统能够将最终 working branch push 到 remote。

### AC-22

最终记录 remote branch 与 final commit SHA。

### AC-23

Agent success + push failure 能被准确表达。

### AC-24

Push failure 可以单独 Retry Publish。

### AC-25

Retry Publish 不重新运行 Agent。

### AC-26

多个 Task 可以基于同一个 Project 并行执行且 Workspace 相互隔离。

### AC-27

一个 Workspace 默认不存在两个同时写入的 Run。

### AC-28

Runtime crash 不应删除 Task Workspace。

### AC-29

Task Cancel 后 Runtime 被正确终止，同时 Workspace 保留。

### AC-30

现有 Handoff / Native State 能力不被破坏。

# 四十五、实现原则

开发过程中遵守以下原则。

### Principle 1

不要将 Project、Workspace、Runtime、Task、Run 的职责混在一起。

### Principle 2

不要通过让 Agent “记得执行某个命令”代替平台能力。

### Principle 3

任何涉及 Credential、Publish、Lifecycle 的重要行为都必须由 Platform enforce。

### Principle 4

Runtime 可以 disposable，但用户开发成果不能因此丢失。

### Principle 5

Workspace 表示 durable code state。

### Principle 6

Native State 表示 Harness-private state。

### Principle 7

Task 表示用户意图。

### Principle 8

Run 表示一次具体 Agent execution attempt。

### Principle 9

Project 表示长期 codebase configuration。

### Principle 10

不要为了本需求破坏已有 Handoff architecture。
