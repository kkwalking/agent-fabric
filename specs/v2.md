# AgentFabric 下一阶段修正需求

请基于当前已经实现的 AgentFabric 代码继续迭代。

本阶段只处理两个明确问题：

1. 清理旧的 AgentFabric 统一 `Session` 模型
2. 打通 Containerized Runtime 下的 Native Resume 闭环

不要在本阶段扩展新的 Workspace 高级能力、Multi-Agent Workflow 或其他无关功能。

---

## 1. 移除旧的 AgentFabric 统一 Session 抽象

当前项目已经明确采用以下设计原则：

> **Same Harness → Native Resume**

> **Different Harness → Handoff**

不同 Agent Harness，例如 Pi 和 OpenCode，应继续使用各自原生的 Session 机制。

AgentFabric 不应该定义或维护一套统一的跨 Harness Session Schema。

因此需要逐步清理现有代码中遗留的旧 `Session` 顶层抽象。

---

## 2. Session 的正确定位

AgentFabric 中不再存在统一的：

`AgentFabric Session`

不同 Runtime / Harness 的 Session 都属于 Harness 自己。

AgentFabric 只需要保存一个不透明的 Native Session Reference，例如：

`RuntimeSessionRef`

该 Reference 只用于：

* 标识 Harness 原生 Session
* 在相同 Harness 下执行 Native Resume
* 记录 Session 所属 Runtime / Harness
* 保存必要的 Runtime-specific Metadata

AgentFabric 不需要理解 Session 内部的数据结构。

---

## 3. 清理旧 Session 数据模型

检查现有代码中旧的统一 `Session` 类型及相关字段。

需要逐步废弃或移除：

* 顶层 `Session` Entity
* Task 对统一 `sessionId` 的依赖
* 统一 Session 生命周期
* 统一 Session Usage / Run 聚合逻辑
* 其他把 Runtime Native Session 当成 AgentFabric Session 的逻辑

最终推荐的数据关系是：

Task

→ Run

→ Runtime

→ RuntimeSessionRef

其中 `RuntimeSessionRef` 属于具体 Runtime / Harness 的 Native Session 引用，而不是一个新的 AgentFabric Session。

---

## 4. 清理旧 Session API

检查当前 API 中与旧统一 Session 模型相关的接口，例如：

* Session List
* Session Create
* Session Detail
* Session Resume
* Session Close
* Session Delete

如果这些接口仍然代表 AgentFabric 自己管理的一套统一 Session，需要废弃或移除。

Native Session 不需要成为一个独立的用户级一级资源。

用户主要操作：

* Task
* Run
* Runtime
* Workspace
* Handoff

Runtime Native Session 可以作为：

* Run Detail
* Task Execution History
* Runtime Metadata

的一部分展示。

---

## 5. UI 中弱化统一 Session

如果当前 Web UI 中存在一级 `Sessions` 页面，并且该页面代表旧 AgentFabric Session 模型，需要逐步废弃。

用户应该主要通过：

* Task Detail
* Run Detail
* Runtime Detail

了解 Native Session 状态。

可以显示：

* Native Session ID / Reference
* Harness Type
* Resume Supported
* Last Used Run
* Runtime Version

但不要让用户误以为 Pi Session 和 OpenCode Session 是同一种 AgentFabric Session。

---

## 6. 保留 Native Resume

移除统一 Session 不代表取消 Resume。

对于相同 Harness：

Pi → Pi

OpenCode → OpenCode

仍然需要优先使用 Harness 自己的 Native Session Resume。

Native Resume 所需要的状态由：

* RuntimeSessionRef
* Harness Native State

共同提供。

---

# 第二部分：打通 Containerized Native Resume

当前 AgentFabric 同时支持：

* Local Runtime Execution
* Containerized Runtime Execution

但 Containerized 模式下的 Harness Native Resume 需要完整闭环。

目标是：

> 使用 Docker Container 执行 OpenCode / Pi 时，也应该保留与本地执行模式相同的 Native Session 和 Harness Event 能力。

---

## 7. Docker 不应该吞掉 Harness Protocol

Docker 只是 Runtime 的执行和隔离载体。

Docker 层不应该把 OpenCode / Pi 的结构化输出全部降级成普通 Shell Output。

例如：

OpenCode Adapter 应继续负责理解 OpenCode 的输出协议。

Pi Adapter 应继续负责理解 Pi 的输出协议。

整体关系应该是：

Harness Adapter

→ Execution Backend

→ Docker Container

而不是：

Harness Adapter

→ Docker

→ 所有输出统一变成 Shell Log

---

## 8. Containerized Harness 需要保留结构化输出

当 OpenCode 或 Pi 在 Docker Container 中运行时，需要让对应 Harness Adapter 能够继续获取原始 stdout / stderr 或结构化输出流。

从而继续执行：

* Harness Event Parsing
* Native Session ID Extraction
* Usage Parsing
* Agent Message Parsing
* Tool Event Parsing
* Error Parsing

Containerized 和 Local 模式应尽可能复用相同的 Harness Output Parser。

---

## 9. Containerized OpenCode Native Session

当 OpenCode 在容器中执行时，需要能够：

* 解析 OpenCode 输出
* 获取 OpenCode Native Session Reference
* 将该 Reference 保存到 Run
* 在后续相同 OpenCode Harness 的 Run 中使用该 Reference Resume
* 保持 OpenCode Native Session 的连续性

不能出现：

Local OpenCode 支持 Native Resume

但：

Containerized OpenCode 不支持 Native Resume

的行为差异。

---

## 10. Containerized Pi Native Session

Pi Runtime 同样需要满足：

* 容器中解析 Pi 原生输出
* 获取 Pi Native Session Reference
* 保存 Native Session Reference
* 后续 Pi → Pi 时执行 Native Resume

Local Pi 与 Containerized Pi 应拥有一致的 Native Session 语义。

---

## 11. Runtime Capability 必须反映真实能力

当前 Runtime Capability 如果声明：

* Supports Native Session
* Supports Native Resume
* Supports Streaming Events

那么这些能力必须在当前 Execution Backend 下真实可用。

例如不能出现：

OpenCode Runtime 声明 `supportsNativeResume = true`

但启用 Docker Execution 后实际上无法恢复 Session。

Runtime Capability 应考虑：

Harness Capability

以及：

Execution Backend Capability

最终暴露真实可用能力。

---

## 12. Native Session State 不能只保存 Session ID

Native Resume 可能不仅依赖一个 Session ID。

OpenCode、Pi 或未来其他 Harness 可能还会把 Native Session 数据保存到：

* Harness Data Directory
* Config Directory
* Cache Directory
* Local Database
* Runtime-specific Files

如果 Container 是 Ephemeral：

Run 完成

→ Container Destroy

那么这些数据不能一起丢失，否则只保存一个 Session ID 可能无法真正 Resume。

---

## 13. 引入 Harness Native State 的持久化概念

需要支持 Runtime / Harness 私有状态的持久化。

该能力可以称为：

`Runtime Native State`

或类似概念。

它与 Workspace 必须明确区分。

### Workspace

保存用户真正关心的工作内容，例如：

* Source Code
* Project Files
* Generated Files
* Working Changes

### Runtime Native State

保存 Harness 自己用于 Native Resume 的私有数据，例如：

* Native Session Data
* Harness Metadata
* Internal Runtime Files
* Native Session Database
* Runtime-specific State

---

## 14. Runtime Native State 必须保持 Opaque

AgentFabric 不应该解析或统一 Runtime Native State。

AgentFabric 只负责：

* Create
* Mount
* Preserve
* Reattach
* Delete

AgentFabric 不应该理解：

Pi 的 Native State

或：

OpenCode 的 Native State

内部具体是什么。

这仍然需要坚持：

> **Harness sessions stay native.**

---

## 15. Ephemeral Container 下的 Native Resume

最终需要支持以下完整流程：

Run #1

→ Create Ephemeral OpenCode Container

→ Attach Workspace

→ Attach OpenCode Native State Storage

→ Execute OpenCode

→ Capture Native Session Ref

→ Persist Workspace

→ Persist OpenCode Native State

→ Destroy Container

随后：

Run #2

→ Same Task

→ Same OpenCode Harness

→ Create New Ephemeral Container

→ Attach Existing Workspace

→ Attach Existing OpenCode Native State

→ Resume using Native Session Ref

→ Continue Task

这样才能真正同时满足：

> **Containers are disposable.**

和：

> **Same Harness → Native Resume.**

---

## 16. Handoff 行为保持不变

本阶段不要改变已有跨 Harness Handoff 模型。

如果：

Pi → OpenCode

仍然执行：

* 保存当前 Workspace
* 生成 Handoff
* 不迁移 Pi Native Session
* 创建新的 OpenCode Native Session
* Attach 同一个 Workspace
* 将 Handoff 提供给 OpenCode
* OpenCode 继续任务

不要尝试：

Pi Session → OpenCode Session

转换。

---

## 17. 最终状态模型

完成本阶段后，建议整体模型保持为：

Task

→ Runs

Run 包含：

* Runtime
* Model
* Workspace
* Container
* RuntimeSessionRef
* Runtime Native State Reference
* Logs
* Events
* Artifacts
* Handoff

其中：

### Workspace

用户长期工作内容。

### RuntimeSessionRef

Harness 原生 Session 的不透明引用。

### Runtime Native State

Harness 原生 Session 所依赖的持久化私有状态。

### Container

可销毁的执行环境。

### Handoff

不同 Harness 之间的语义交接。

---

## 18. 本阶段验收目标

本阶段完成后应满足以下行为。

### Same Harness + Local

Pi → Pi

支持 Native Resume。

OpenCode → OpenCode

支持 Native Resume。

### Same Harness + Docker

Containerized Pi → Containerized Pi

即使前一个 Container 已销毁，仍然能够 Native Resume。

Containerized OpenCode → Containerized OpenCode

即使前一个 Container 已销毁，仍然能够 Native Resume。

### Different Harness

Pi → OpenCode

执行 Handoff。

OpenCode → Pi

执行 Handoff。

不进行 Native Session 转换。

### Session Model

AgentFabric 不再维护统一跨 Harness Session。

只保留 Harness-specific：

* RuntimeSessionRef
* Runtime Native State

---

## 19. 本阶段核心设计原则

请严格遵循：

> **Containers are disposable.**

> **Workspaces are durable.**

> **Harness sessions stay native.**

> **Runtime native state is opaque.**

> **Same Harness means Resume.**

> **Different Harness means Handoff.**

AgentFabric 负责 Runtime 的执行、隔离、生命周期和状态挂载，但不应该重新实现或统一不同 Agent Harness 的 Session 机制。

本阶段最终目标是让 AgentFabric 的 Native Resume 模型在 Local 和 Containerized 两种执行方式下保持一致，并彻底移除旧的统一 AgentFabric Session 概念。
