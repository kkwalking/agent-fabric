# AgentFabric：看板与本地 Agent 会话（v13）

本版为 AgentFabric 增加一个**看板（Board）**产品面：用四列管理多个本地 Coding Agent CLI，
每张卡片拥有自己的工作目录与一个可交互的会话。有 TUI 的 agent（Claude Code / Pi /
OpenCode）把终端嵌进 Web UI（xterm，与 Cline kanban 相同的交互）；DSH 没有 TUI，改为
由 AgentFabric 通过 ACP（Agent Client Protocol）驱动 `dsh --profile acp`，在卡片详情里
渲染自己的聊天界面。第二期的 `structured` 模式仍把 harness 的消息投影成统一 UI。

本文件是实现依据。实现以本文件为准；与既有 `v1`–`v12` 冲突的地方，以本文件为准并
在 README 里说明边界。

---

## 一、目标与非目标

### 目标

1. 四列看板：`backlog` / `in_progress` / `review` / `trash`（UI 上叫 Backlog / In Progress /
   Review / Done），支持拖拽与自动流转。
2. 一个看板项目 = 一个任意本地目录（folder-first，不要求 Git；兼容普通 Git 仓库、
   多 Git 仓库父目录、Google `repo` 工作区）。
3. 一张卡片 = 一个任务 + 一次可交互的 agent 会话；卡片上选择 agent、模型、权限模式、
   执行模式（direct / worktree）。
4. 本地宿主执行，两条传输：Claude Code / Pi / OpenCode 用 `node-pty` 启动，TUI 通过
   xterm.js 呈现在卡片详情里（输入、resize、停止都可用）；DSH 没有 TUI，用 ACP stdio
   启动 `dsh --profile acp`，卡片详情是 AgentFabric 渲染的聊天（消息、思考、工具活动、
   权限询问、继续对话、取消）。
5. 会话状态回传：Claude / OpenCode 用 harness hooks 自动进入 Review；DSH 由 ACP 自己在
   turn 结束时报告（`end_turn` / `cancelled`），不需要 hooks；Pi 没有 hooks，用手动
   Mark for review。状态变化驱动卡片在 In Progress ↔ Review 之间自动移动。
6. 第二期：为卡片增加 `structured` 执行模式，走既有的 RuntimeAdapter + RunEvent 流，
   用统一消息 UI 渲染；`terminal` 模式保留为交互/排障入口。

### 非目标（v13 第一期）

- 不做 diff review / checkpoint / apply / commit / PR / auto-review（这些能力依赖
  turn checkpoint 与多仓 change set，属于后续版本）。
- **不做 isolated 目录拷贝、Docker 或其他隔离 Runtime**：worktree 就是第一期的隔离手段。
- **不加 Direct 写者锁**：同一 BoardProject 允许多个 Direct 会话并行。
- 不做卡片依赖链 / 自动启动链 / auto-commit。
- 不做 Cline 原生 chat 路径（`@clinebot/*` 不进入本仓库）。
- 不做移动端布局；不做 Windows 的进程组细节（先保证 macOS/Linux）。
- 不把看板卡片接进 Project Coding Task 的生命周期（不触发 validation / publish）。
- 不整体搬运 bruce-kanban（它绑死 tRPC / Cline SDK / `~/.cline/kanban`）。只借鉴其
  PTY、终端 / 协议、状态机、agent 启动契约的实现方式。

### 已定决策（用户已拍板，实现时不得再改）

1. **原生做进 agent-fabric**，不把 bruce-kanban 作为独立进程/包接入。
2. **本地宿主执行**（与 bruce-kanban 相同）：PTY 或 ACP stdio 进程。这是看板的独立
   执行路径，明确不走 Project Coding Task 的隔离 Runtime；`allowHostExecution` 的语义
   不适用于看板。
3. **第一期范围**：4 列 + 卡片 + 内嵌终端 / DSH 聊天 + 启停 + 自动状态；不做 diff/commit/PR。
4. **DSH 第一期用 ACP（`dsh --profile acp`）驱动，卡片详情是交互聊天**：DSH 自带的
   surface 没有交互 TUI（社区另有独立的 `dsh-tui` 启动器；看板仍选 ACP，因为结构化的
   消息 / 工具 / 权限展示与 `session/resume` 续跑都在协议内），headless 是一次性输出，
   两者都不适合交互；ACP 是 DSH 提供的自动化 stdio 协议，AgentFabric 自己渲染消息、思考、
   工具活动与权限询问，并允许继续对话。第二期的 `structured` 模式仍用既有 RuntimeAdapter
   做统一 UI，那是 RunEvent 投影，与这条 ACP 路径不是同一件事。
5. **执行模式 = Direct / Worktree**：勾选 worktree 时用 `git worktree add --detach` 切出
   独立工作树；只有项目根自身是 Git 仓库才可用。Isolated/Docker 不实现。
6. **同一 BoardProject 不限制 Direct 会话数量**：并发写冲突由 agent 自己处理。
7. **Hooks 自动流转**：Claude / OpenCode 的 `Stop` / `session.idle` 自动进 Review，
   用户输入自动回 In Progress；DSH 不需要 hooks（ACP 自己报告 turn 结束）；Pi 无 hooks
   用 Mark for review 兜底。

## 二、概念模型

### 2.1 BoardProject（看板项目）

用户选择的一个本地目录，是看板与卡片的工作区边界。与既有 `Project`（Git Source +
Coding Task）是不同概念，互不复用。

```ts
type BoardWorkspaceType = "none" | "git" | "multi-git" | "google-repo";

interface BoardProject {
  id: ID;
  name: string;
  /** 用户选择的目录，永远不向上寻找父级 Git 根。 */
  rootPath: string;
  workspaceType: BoardWorkspaceType;
  /** 发现失败只降级为 none + warning，永远不阻止创建/启动。 */
  discoveryWarning?: string;
  defaultAgentId?: AgentKind;
  defaultExecutionMode?: ExecutionMode;
  defaultPermissionModeId?: string;
  createdAt: string;
  updatedAt: string;
}
```

约束：

- 不要求 `.git`：普通目录就是合法 BoardProject。
- 添加项目时**不静默** `git init`：目录不是 Git 仓库时，界面先询问「Add without Git」
  或「Initialize Git repository」；选择后者才 `git init` + 初始 commit（worktree 需要至
  少一个 commit）。这条选择由用户做出，接口用 `gitInit: "ask" | "init" | "skip"` 表达。
- `rootPath` 是事实；发现（discovery）只用于展示与可选能力，不改变 root。
- 同一目录只能有一个 BoardProject（`kanban-project-duplicate`）。
- 删除 BoardProject 不删除用户目录；只删平台记录。

### 2.2 Card（卡片）

```ts
type BoardColumnId = "backlog" | "in_progress" | "review" | "trash";
type ExecutionMode = "direct" | "worktree";
type AgentKind = "claude" | "pi" | "opencode" | "dsh";

interface Card {
  id: ID;
  projectId: ID;
  title: string;
  prompt: string;
  column: BoardColumnId;
  agentId: AgentKind;
  model?: string;
  /** 该 agent 自己的权限模式 id；缺省取项目默认。 */
  permissionModeId?: string;
  permissionPolicy?: { autonomous: boolean; extraArgs?: string[] };
  executionMode: ExecutionMode;
  /** worktree 卡片的基 ref（分支/tag/commit）；缺省用项目 HEAD。 */
  baseRef?: string;
  /** 最近一次会话（没有则为空）。 */
  sessionId?: ID;
  createdAt: string;
  updatedAt: string;
}
```

约束：

- 卡片创建后 agent / executionMode / baseRef 可在**未启动**时修改；运行中不可改（与
  bruce-kanban 一致）。
- 标题在创建时由 prompt 派生（首个非空行 → 去掉外层标签 → 取首句 → 最多 80 字符），
  用户显式填写的标题优先。
- `trash` 是 Done 列的内部 id：进入 trash = 停止会话；从 trash 恢复回 `review`。
- 4 列迁移规则由服务端与前端共同遵守（见 §六）。

### 2.3 CardSession（会话）

```ts
type SessionStatus =
  | "starting"
  | "running"
  | "awaiting_review"
  | "needs_attention"
  | "failed"
  | "interrupted"
  | "stopped";

interface CardSession {
  id: ID;
  cardId: ID;
  agentId: AgentKind;
  /** 实际工作目录：direct = project.rootPath；worktree = git worktree 路径。 */
  cwd: string;
  executionMode: ExecutionMode;
  /** 会话传输：`pty` = TUI 字节流；`acp` = ACP stdio（DSH）。 */
  transport: "pty" | "acp";
  status: SessionStatus;
  /** 进程 pid / 进程组；服务端内存态，不持久化。 */
  pid?: number;
  /** harness 自己的 session id，用于 resume（能拿到时才写）。 */
  nativeSessionId?: string;
  startedAt: string;
  endedAt?: string;
  exitCode?: number;
  error?: string;
}
```

状态机（服务端权威，前端只做展示与乐观更新）：

```text
starting → running        spawn 成功 / 收到第一条输出 / ACP 握手完成（session/new 返回）
running  → awaiting_review  hooks: to_review（Claude/OpenCode）；ACP: turn 以 end_turn 或 cancelled 结束
running  → needs_attention  hooks: permission request（Claude/OpenCode）；ACP: session/request_permission（Ask 模式）
running  → failed           进程退出码非 0 / spawn 失败 / ACP 握手失败 / ACP 进程意外退出
running  → stopped          用户 stop / 卡片进 trash
running  → interrupted      服务端重启时仍 running
awaiting_review → running   hooks: to_in_progress（用户继续输入 / agent 重新开始）/ 聊天里发新 prompt
awaiting_review → stopped   用户 stop / 卡片进 trash
needs_attention → running   用户处理权限后继续（ACP 答完权限请求）
interrupted → starting      用户 restart / resume
failed / stopped → starting 用户 restart
```

第一期不做「重启后自动恢复进程」（PTY 或 ACP）：进程随服务端退出而死。重启时把
`running` / `starting` 一律写成 `interrupted`，卡片保留在 `in_progress`，用户可 restart
或 resume。ACP 的 session id 记进 `nativeSessionId`，并可用 ACP 的 `session/resume`
接回同一个会话（详见 §3.4）；`session/load` 仍不支持——历史由 AgentFabric 自己保存和
显示，DSH 只恢复自己的模型上下文。

## 三、执行模型

### 3.1 启动一张卡片

1. 校验卡片所在列：只有 `backlog` 可以启动；成功后移到 `in_progress`。
2. 解析工作目录：
   - `direct` → `project.rootPath`；
   - `worktree` → `dataDir/kanban/worktrees/<sessionId>`，用
     `git -C <root> worktree add --detach <path> <baseRef ?? HEAD>` 创建（见 §3.3）。
3. **不限制同一 BoardProject 的并发 direct 会话**：用户明确接受多个 agent 直接改同一
   工作区，冲突由 agent 自己处理；平台不加写者锁。
4. 由 agent catalog 生成 argv / env（见 §四），cwd = 工作目录，然后按 `transport` 启动：
   - `pty`：注入 hooks 配置与 per-session hook token，`node-pty` spawn；
   - `acp`：spawn `dsh --profile acp`，在 stdio 上依次 `initialize` → `session/new
     {cwd, mcpServers: []}` → `session/prompt {prompt:[text]}`；prompt 走协议、不进 argv。
5. 建 CardSession（`transport` 在建记录时写入），hooks 路径先写 `running` 再 spawn（hook
   可能在进程启动瞬间回调，不能被后续 running 写覆盖）；ACP 路径在 `session/new` 返回
   后写 `running`，并把返回的 session id 记进 `nativeSessionId`。spawn / 握手失败
   settle `failed`。
6. 结束语义按 transport 区分：
   - `pty`：进程退出码 0 且无 signal → `awaiting_review`；否则 `failed`。hook 的
     `to_review` 优先于退出码（TUI 可能继续开着）。
   - `acp`：一个 turn 结束不结束进程——`stopReason: "end_turn"` 或 `"cancelled"` →
     `awaiting_review`（卡片进 Review），进程继续存活以便继续对话；其他 stopReason →
     `failed`。进程意外退出（非用户 stop）→ `failed` 并记录 exit code。

### 3.2 停止 / 重启 / 恢复

- **stop**：向整个进程组发 SIGTERM（`process.kill(-pid)`），5 秒后 SIGKILL；
  session → `stopped`；不删除工作目录。ACP 先把待答的权限请求按 cancelled 回掉、best-effort
  `session/close`，settle `stopped` 后再等进程真正退出（最多 3.5s），最后把聊天 socket 以
  `agent_status {status:"stopped", live:false}` 关闭——这样 Stop 之后立刻重开卡片，看到的是
  已停止的会话与保存好的转录，而不是半死的进程。
- **restart**：同一卡片创建新 session（新 PTY / 新 ACP 进程）；旧 session 保留记录，
  旧 ACP 聊天转录保留到卡片被删除。
- **resume**：ACP 会话有 `nativeSessionId` 时，卡片详情的聊天在进程消失后显示
  **Resume session**：服务端重新 spawn `dsh --profile acp`，走 `initialize` →
  `session/resume {sessionId, cwd, mcpServers: []}` 接回同一 DSH 会话，成功后记录状态回到
  `awaiting_review`（清掉 `endedAt` / `error` / `exitCode`）并可继续发 prompt。
  ACP 不回放旧 update（`session/load` 不支持），历史由 AgentFabric 保存的转录显示。
  DSH 未在 `initialize` 广告 `session/resume`、会话已被其他进程占用、或 cwd 不匹配时
  明确失败（`kanban-session-resume-failed`），不静默降级成新会话。PTY 会话没有 resume；
  Claude/Pi/OpenCode 仍用 restart 起新会话（`--continue` 未接入）。

### 3.3 Worktree 工作区

- 只有 BoardProject 的 `workspaceType === "git"`（项目根自己就是 Git 仓库）才提供
  `worktree` 模式；非 Git / multi-git / google-repo 一律明确拒绝
  （`kanban-worktree-unavailable`），不静默退回 direct。
- 每个 worktree 会话在 `dataDir/kanban/worktrees/<sessionId>` 创建
  `git worktree add --detach <path> <baseRef ?? HEAD>`；base ref 可以是本地分支 / tag /
  commit，创建前先 `git rev-parse --verify <ref>^{commit}`，不存在则以
  `base-ref-not-found` 明确失败。分支留在用户手里，第一期不自动 commit。
- 源工作树只读；worktree 与源仓库共享 object store，改动不落回源目录。
- 第一期不自动删除 worktree（用户可能还要查看）；卡片/项目永久删除时也不删除
  worktree，避免误删未提交改动。后续版本再加显式清理。
- **不实现 isolated 目录拷贝 / Docker 隔离**：看板不是隔离 Runtime，worktree 就是
  第一期的隔离手段。

### 3.4 重启恢复

- 启动时扫描 `kanbanSessions` 中非终态 → 写 `interrupted`；卡片保持原列。
- 不自动重跑 agent；与 v11-hardening「重启后不得自动重新运行 Agent」一致。
- ACP 的聊天转录由 `AcpChatProjector` 投影后**落盘**在
  `dataDir/kanban-chats/<sessionId>.json`（每个 session 一个原子写的 JSON 文档，不写进
  db.json）；流式 chunk 期间防抖写入，turn 结束 / 权限请求 / 进程退出 / `stop` 立即写，
  服务端关闭时同步写。重启（或 stop / agent 退出）后打开旧卡片：聊天 WS 照常 attach，
  先 replay 已保存的转录（`agent_snapshot` 的 `items`），`live:false` +
  `canResume:true`，composer 禁用并显示 **Resume session**；点 Resume 才接回进程（见 §3.2）。
  旧 session 的转录在卡片/项目被删除时一起清理。
- 升级前创建、从未写过转录的 session 打开后没有历史可显示（不做读取时回填），但仍可
  Resume（`nativeSessionId` 已在记录里）。

## 四、Agent 契约（本地 PTY / ACP）

catalog 条目字段：

```ts
interface KanbanAgentEntry {
  id: AgentKind;
  label: string;
  binary: string;
  /** 启动任务时的基础参数（不含 prompt）。 */
  baseArgs: string[];
  /** prompt 的交付方式：位置参数 / --prompt / 协议（acp）。 */
  promptArg: "positional" | "flag:--prompt" | "acp";
  /** 与 agent 的传输方式：`pty`（TUI 字节流）或 `acp`（Agent Client Protocol）。 */
  transport: "pty" | "acp";
  permissionModes: { id: string; label: string; args: string[]; env?: Record<string,string>; risky?: boolean }[];
  defaultPermissionModeId: string;
  modelFlag: string | null;
  /** 是否支持 harness hooks（状态回传）。 */
  hooks: boolean;
  /** resume 参数模板；null 表示不支持。 */
  resumeArgs: ((nativeSessionId: string) => string[]) | null;
  /** 交互式 TUI 能力；false 时没有终端可嵌入（DSH 走 ACP 聊天）。 */
  interactiveTui: boolean;
  installHint: string;
}
```

第一期条目：

| id | binary | 启动 | 权限 | hooks | resume | 备注 |
|---|---|---|---|---|---|---|
| `claude` | `claude` | `claude <prompt>` | `--permission-mode default/plan/acceptEdits/auto`、`--dangerously-skip-permissions`（risky） | `--settings <hooks.json>` | `--continue` | 启动前预写 workspace trust（62d16a0 的修复） |
| `pi` | `pi` | `pi <prompt>` | `--approve` / `--no-approve` | 无 | `--continue` | 状态靠进程生命周期 / 输出静默 |
| `opencode` | `opencode` | `opencode --prompt <prompt>` | `--auto`（risky）/ 默认 | `OPENCODE_CONFIG` 指向生成的 plugin 配置 | `--continue` | 2.x 版本漂移风险，启动前做 `--version` 检测 |
| `dsh` | `dsh` | `dsh --profile acp`（prompt 走 ACP 协议，不进 argv） | Ask（`session/request_permission` 询问卡片）/ Auto-approve（自动选 allow 选项，risky；没有 allow 选项时仍会询问） | 无（ACP 自报 turn 结束） | ACP `session/resume {sessionId, cwd}`（`nativeSessionId`；需 agent 在 `initialize` 广告 resume 能力） | 无 TUI，卡片详情为 AgentFabric 渲染的 ACP 聊天；`transport: "acp"`、`interactiveTui: false`；模型/推理强度走 ACP config option（无 model flag）；转录落盘于 `dataDir/kanban-chats/` |

通用约束：

- 模型（PTY）：有 `modelFlag` 时追加 `--model <id>`；没有就忽略（不伪造）。
- 模型 / 推理强度（ACP）：握手（`session/new` 或 `session/resume`）返回的
  `configOptions` 是该会话的权威目录（DSH：`model` 按 provider 分组、`reasoning_effort`
  为 flat select，value 对协议不透明、形如 `["provider","model"]`）。卡片的 `model`
  在**第一次 turn 前**由 `session/set_config_option` 应用：按「完整 value → model id →
  显示名」大小写不敏感匹配，匹配不到就 `kanban-agent-model-unavailable` 失败（绝不静默
  回落默认模型）；`reasoningEffort` 同理（`kanban-agent-effort-unavailable`）。应用结果
  投影成 `KanbanSession.modelRoute {value, provider?, model?, label?}` 与
  `reasoningEffort` 落进记录，卡片详情显示的是**实际**路由。聊天里切换用
  `set_config {configId, value}`，服务端调 `session/set_config_option`、广播完整的新
  `configOptions`（其他标签页同步），下一个 turn 生效；agent 自己发的
  `config_option_update` 也会被同步。`usage_update` 只更新顶栏 token 用量，不进转录。
- prompt：PTY 路径作为 argv 的一个元素交付（绝不拼 shell 字符串）；ACP 路径在握手后
  通过 `session/prompt` 交付。
- 权限：默认取 `defaultPermissionModeId`；绝不自动加高风险参数（沿用 fork 的
  「autonomy 与 permission 分离」原则）。DSH 的权限模式是运行时策略而不是 argv：
  `Ask` 把 ACP 的权限请求交给卡片，`Auto-approve` 自动选 ACP 给出的 allow 选项（没有
  allow 选项时落回询问）。
- 系统指令：第一期不注入 Agent Profile 的 systemInstructions；卡片只有 prompt。
- 环境：注入 `AGENTFABRIC_KANBAN_CARD_ID` / `AGENTFABRIC_KANBAN_PROJECT_ID`（调试用）；
  PTY 路径额外注入 `AGENTFABRIC_KANBAN_SESSION_ID` / `AGENTFABRIC_KANBAN_HOOK_URL` /
  `AGENTFABRIC_KANBAN_HOOK_TOKEN`（hooks 用）。不注入任何 Secret（看板不吃
  Task/Project 的 secretIds）。
- 二进制检测：启动前 `which <binary>`；缺失返回 `kanban-agent-not-installed`，给出
  installHint，不静默换 agent。
- DSH：启动前检查 `$DSH_HOME/profiles/acp`（`DSH_HOME` 缺省 `~/.dsh`）；缺失时用
  `dsh --profile acp --help` 探测（launcher 会按随包模板生成 profile，探测结果按进程
  缓存），仍不可用返回 `kanban-agent-profile-missing`，提示升级 DSH（0.2.1+ 自带 acp
  profile）。
- ACP 客户端能力：只声明文本（`fs.readTextFile` / `fs.writeTextFile` / `terminal` 全为
  false），所以除 `session/request_permission` 之外的 server → client 请求一律回
  JSON-RPC `-32601`；`initialize` / `session/new` / `session/resume` / `session/close`
  分别有 30s / 30s / 30s / 5s 超时，`session/prompt` 不设超时（长 turn 由 Stop / Cancel
  结束）。resume 能力取自 `initialize` 返回的
  `agentCapabilities.sessionCapabilities.resume`，未广告时直接拒绝 resume（不尝试调用
  未声明的方法）。

### 4.1 Hooks（Claude / OpenCode，已实现）

- **per-session capability token**：每次 start 生成随机 24 字节 token；只存在服务端内存
  与 agent 环境里，随会话结束销毁。它只能移动自己那张卡，不是全局 API token。
- **回调端点**：`POST /kanban-hooks/ingest`，body
  `{sessionId, event: "to_review"|"to_in_progress"|"needs_attention"}`，header
  `x-kanban-hook-token`。刻意放在 `/api` 之外：全局 token 中间件不覆盖它，端点自己
  做 constant-time 校验（错误 token → 403 `kanban-terminal-unauthorized`）。
- **Claude**：生成 `dataDir/kanban/provisioning/<sessionId>/claude-settings.json`，通过
  `--settings` 注入；`Stop → to_review`、`UserPromptSubmit → to_in_progress`、
  `Notification(permission_prompt) → needs_attention`。每条 hook 是 `curl` 一次性回调，
  失败静默（不能阻断 agent）。
- **OpenCode**：生成 `opencode.json` + `kanban-plugin.mjs`，通过 `OPENCODE_CONFIG` 注入；
  plugin 监听 `session.idle` / `session.status(idle)` → `to_review`，`busy` / `error` →
  `to_in_progress`，`permission.ask` → `needs_attention`；用 `fetch` 回调。
- **状态语义**：`to_review` 只把 session 标成 `awaiting_review` 并把卡移到 Review，**不杀
  PTY**（TUI 继续开着）；`to_in_progress` 移回 In Progress；`needs_attention` 不当作
  完成。重复/过期事件幂等。
- **用户输入也是新 turn**：卡片在 Review 时，前台往终端输入任意字节会把卡移回 In
  Progress（不依赖 hook）；ACP 会话在聊天里发新 prompt 同理（服务端发 prompt 前把卡
  移到 In Progress）。
- **ACP（DSH）不需要 hook**：turn 结束、权限询问与进程退出都由 ACP 自己报告；服务端
  把这些合成事件写进 `lastHookEvent` 便于调试（`prompt` / `turn_end` /
  `turn_cancelled` / `turn_failed` / `turn_error` / `permission_request` /
  `permission_answered`），它们不走 `/kanban-hooks/ingest`。
- **Pi**：没有 hooks（保留手动 Mark for review）。

## 五、会话传输协议

### 5.1 终端 WebSocket

- 端点：`GET /api/kanban/sessions/:sessionId/terminal`（Upgrade）。
- 鉴权：复用 `af_token` cookie 或 `Authorization: Bearer`；两者都没有 → `401` 并关闭。
  不从 query string 读 token（既有安全约定）。校验 Origin 必须是本机同源（loopback）。
- 一个 session 一条 PTY，多客户端共享；每个客户端独立 backpressure。

### 5.2 终端帧

- **IO 通道**：二进制帧 = PTY 原始字节（双向）。前端 xterm `onData/onBinary` 直接写。
- **控制通道**：同一连接上的 JSON 文本帧（或以首字节区分；实现可简化为两条 WS）：
  - client → server：`{type:"resize",cols,rows}`、`{type:"stop"}`、
    `{type:"restore_request"}`、`{type:"output_ack",bytes}`
  - server → client：`{type:"state",status}`、`{type:"exit",code}`、
    `{type:"restore",data,cols,rows}`、`{type:"error",code,message}`

实现取舍：第一期可以只开一条 WS，用「首字节 0x00 = JSON 控制帧，其余 = PTY 字节」
区分；但优先按 bruce-kanban 的做法拆成 io + control 两条，代码更清晰、背压独立。

### 5.3 回放与背压

- 服务端为每个 session 维护 headless xterm（`@xterm/headless` + serialize），
  scrollback 上限 10k 行；新客户端 attach 先收 `restore` 快照，再收增量。
- PTY 输出 → headless 写入 → 各客户端；单客户端积压超过 1MB 时暂停该客户端的
  PTY 输出（`pause`/`resume`），其余客户端不受影响。
- 不做自动重连；卡片详情关闭即 detach，重新打开重新 attach + restore。
- 服务端退出/会话结束：销毁 headless 实例，释放缓冲；不把终端字节写入 db.json。

### 5.4 安全

- 终端输入 = 在宿主上执行任意命令：看板只监听 loopback（沿用 `AGENTFABRIC_HOST`
  默认），WS 必须鉴权；非 loopback 绑定要打印与现有 API 同级的警告。
- 原始终端输出可能包含密钥；不写入事件日志、不返回 API 响应、不落盘（第一期）。

### 5.5 ACP 聊天 WebSocket（DSH）

- 端点：`GET /api/kanban/sessions/:sessionId/agent`（Upgrade）；鉴权与 Origin 规则和
  5.1 完全相同（`af_token` cookie 或 Bearer、loopback 同源），只走 JSON 文本帧。
- 一个 session 对应一个 ACP 进程；多客户端可同时 attach 同一会话，各自收到同一份转录。
  attach 先发 `agent_snapshot {items, status, running, live, canResume, resuming,
  hasTranscript, nativeSessionId?, permissions}`，之后按变化推送以下帧：
  - server → client：`agent_item {item}`（按 `id` upsert）、`agent_status {status,
    running, live, canResume, resuming}`、`agent_permission {request}`、
    `agent_permission_answered {requestId}`（任一客户端回答后广播，其他副本禁用按钮）、
    `agent_error {code, message}`（attach 失败时发完即关闭）。
  - client → server：`prompt {text}`、`cancel`、`resume`、`set_config {configId,
    value}`（模型 / 推理强度等 ACP config option）、`permission {requestId,
    optionId|null}`（`null` 是 ACP 的 cancelled outcome）、`stop`。
  - `agent_composer {live, canResume, resuming, configOptions, usage?}` 是聊天控件
    状态：模型/强度下拉的选项与当前值、上下文 token 用量。agent 自己的
    `config_option_update` 与每次配置变更都会广播它。
- attach 校验：session 不存在 / 不是 ACP 会话分别回 `kanban-session-not-found` /
  `kanban-session-not-agent` 并关闭。进程不在本服务端**不再是 attach 失败**：照常回
  snapshot（`items` 来自保存的转录，`live:false`，`hasTranscript` 说明是否有历史，
  `canResume` 表示 `nativeSessionId` 可接回），客户端因此能查看历史并发起 resume。
  **提示语在 paused 状态下照常可用**：`prompt` 到达时服务端先 `ensureAgent`（复用存活
  进程 → 否则 `session/resume` 接回 → 没有记录才新起会话），接好后把这条消息作为正常
  turn 发出；并发到达的 prompt 共享同一次 attach，不会收到假的 "still starting"。
  上一轮没结束又发 prompt 仍回 `kanban-agent-busy`；会话已 stop/删除回
  `kanban-session-not-live`；resume 失败回 `kanban-session-resume-failed`。反向地，
  对 ACP 会话开 terminal WS 会得到 `kanban-session-not-terminal`；session id 的
  percent-encoding 非法时 upgrade 以 HTTP 400 拒绝（不在 upgrade 监听器里抛异常，避免
  带崩整个服务端）。
- 转录由 `AcpChatProjector` 从 `session/update` 投影：`agent_message_chunk` → 助手消息、
  `agent_thought_chunk` → Thinking、`tool_call` / `tool_call_update` 按 `toolCallId`
  upsert；`user_message_chunk`、`usage`、`plan`、config 等更新不产生聊天行。转录按
  session 落盘（见 §3.4），读取时只解析自己的文档格式，损坏或版本不符视为没有历史，
  不做读取时修补。

## 六、看板规则

固定四列，顺序：`backlog` → `in_progress` → `review` → `trash`。

用户拖拽白名单（与 bruce-kanban 对齐）：

| 来源 → 目标 | 允许 | 行为 |
|---|---|---|
| backlog → in_progress | 是 | 启动会话（等价 play） |
| 任意 → trash | 是 | stop 会话；卡片进 Done |
| trash → review | 是 | 恢复卡片；不自动重启，用户再 play |
| in_progress ↔ review | **仅程序 / 显式按钮** | 由 session 状态或卡片详情的 Mark for review 驱动；用户拖拽拒绝 |
| backlog → review | 否 | — |
| 其他 | 否 | — |

程序化流转（两种 transport 同一套列规则，触发源不同）：

- `running` / `starting` → 卡片在 `in_progress`。
- `awaiting_review` → 卡片移到 `review`（从 in_progress）。
- `needs_attention` → 卡片留在 `in_progress`，卡片上显示 Needs Attention（不误判完成）。
- `failed` → 留在 `in_progress`，显示失败原因与 retry。
- `interrupted` → 留在 `in_progress`，显示 restart/resume。
- `stopped`（stop / 卡片进 trash）→ 进程被结束，卡片按用户动作停在 Done 或原列。

hooks 已接线：Claude / OpenCode 在 `Stop` / `session.idle` 时自动进入 Review（PTY
保持运行），用户输入或 `UserPromptSubmit` 时自动回 In Progress。DSH 走 ACP：一个 turn
以 `end_turn` 或 `cancelled` 结束即进 Review，**进程不退出**；在聊天里发新 prompt 就
回 In Progress；`session/request_permission`（Ask 模式）把 session 标成
`needs_attention` 并把允许/拒绝卡片插进聊天，答完回 `running`。Pi 没有 hooks，卡片
详情提供显式的 **Mark for review** 兜底（所有 agent 都保留这个按钮）。`USER_MOVES`
允许 `in_progress → review`，但 UI 的**拖拽**规则仍拒绝该方向，避免误拖把运行中的
卡片当成已审。

服务端是列迁移的权威：`POST /api/kanban/cards/:id/move` 校验白名单；前端乐观更新，
失败回滚。第一期没有依赖链。

## 七、Web UI

新增路由 `/kanban`（导航 Resources 组新增 **Kanban**）。页面结构：

```text
BoardView
├ ProjectNav（左栏：BoardProject 列表 + 每列卡片数；显示 workspaceType）
├ Board（4 列等宽，列内滚动）
│ └ BoardColumn × 4 → Card × N（Backlog 列顶部有 Create task 入口）
├ CardDetail（全屏 overlay）
│ ├ CardHeader（标题、agent/model、Direct|Worktree、状态、start/stop/restart/trash）
│ └ 会话面板（按 session.transport 二选一）
│   ├ TerminalPanel（xterm 单例；Claude Code / Pi / OpenCode）
│   └ AcpChat（DSH：消息 / Thinking / 工具活动 / 权限卡片 / composer / Cancel）
├ AddProjectDialog（Server path / Git clone 两个 tab）
└ TaskCreateDialog（prompt、标题、agent/model/权限、Direct|Worktree + base ref）
```

ACP 聊天面板（`AcpChat`）：

- 顶栏状态 pill 跟服务端 session 状态一致（connecting / live / working / idle /
  needs attention / exited / disconnected / error）；agent 工作时显示 spinner。
- 助手消息按 Markdown 渲染；Thinking 默认折叠成 `<details>`；工具调用是一行带状态点
  的条目（running / done / error），可展开看 input / output / error。
- 待答的权限请求以卡片插入到它发生的位置，按钮由 ACP 给出的 options 生成（allow_*
  用 primary，reject_* / cancel_* 用 danger），答过即禁用。
- composer：socket 活着且没有 turn 在跑时可输入；Enter 发送、Shift+Enter 换行；turn
  进行中输入框锁定并显示 **Cancel**（发 `session/cancel`，只结束当前 turn）；进程不在
  本服务端时明确提示从卡片操作重启。关闭详情只 detach，记录留在服务端内存；不自动重连。

创建流程（复刻 Cline kanban 的交互与判断）：

- **Add project**：对话框内两个入口。
  - *Server path*：服务端目录自动补全（`GET /api/kanban/fs`）——输入框按「父目录 + 前缀」
    列出可进入的目录，条目显示是否为 Git 仓库；支持 `~`。目录不是 Git 仓库时，先显示
    「This folder is not a Git repository」确认区，由用户选择 **Add without Git** 或
    **Initialize Git repository**。
  - *Git clone*：Git URL + Clone into（目录自动补全）+ Folder name（默认取仓库名）；
    目标目录非空会明确失败，失败后不留半成品目录。
  - 项目名默认取目录名；同一个目录不能重复添加；添加成功后自动选中该项目。
- **Create task**：Backlog 列顶部按钮或 `c` 快捷键打开对话框。
  - 字段：prompt；可选标题（留空时占位符实时显示派生标题）；Agent（Claude Code / Pi /
    OpenCode / DSH，未安装的置灰并给出安装提示）；Model（仅 agent 声明了 model flag 时）；
    Permission mode（仅 agent 声明了非 default 的权限模式时；一个非 default 模式也显示，
    否则 DSH 的 Ask/Auto、OpenCode 的 Auto 无法在选择器里选到）；Workspace（Direct /
    Worktree，Worktree 仅 Git 项目可用）；Worktree base ref（列出本地分支，默认当前分支，必选）。
  - `⌘/Ctrl+Enter` = 创建；`⇧⌘/Ctrl+Enter` = 创建并立即启动；`Esc` 关闭。
  - **Create more**：创建后保留对话框继续录入（对话框级状态，不因表单重置而丢失）。
  - **Split into N tasks**：prompt 是编号/项目符号列表时，拆成 N 行分别创建或启动。
  - 表单用该项目上次的选择（agent / model / permission / workspace / baseRef）预填；
    项目自身的 `defaultAgentId` / `defaultExecutionMode` 优先于内置默认值。

终端实现要求（来自 bruce-kanban 的踩坑）：

- xterm 6 + fit / web-links / clipboard（unicode11 可选）；**不要 minify**
  （会坏 DECRQM/requestMode，TUI 花屏）；单独 chunk。
- 每个卡片一个 `Terminal` 实例，用屏外 parking DOM 保活；不要把实例放进会被
  unmount 的 React 组件里。
- `ResizeObserver` 50ms 防抖 → `fit()` → 发 cols/rows；容器隐藏（display:none）时
  不 fit，避免 2×1 错误尺寸。
- 字体加载完成后重新 fit；浅色主题显式 ANSI palette（不 invert）；深色继承默认。
- `/kanban` 用 agent-fabric 现有 CSS token，不引入 Tailwind/Radix/dnd；拖拽用原生
  HTML5 drag 或极小实现。

第二期在同一 CardDetail 里增加 `structured` 模式的统一消息视图，复用 TaskThread 的
消息渲染（那是 RunEvent 投影，不是第一期的 ACP 聊天）；`Terminal` 在 structured
模式下保留为 "Open terminal"。

## 八、REST API

```text
GET    /api/kanban/fs?path=                目录补全：{rootPath, currentPath, parentPath, entries[]}
                                            （entries 含 name / path / isGitRepository）
GET    /api/kanban/projects
POST   /api/kanban/projects                 {path?, gitUrl?, folderName?, name?, gitInit?}
                                            gitInit: "ask"(默认) | "init" | "skip"
                                            非 Git 目录且 ask → 409 {code:"kanban-project-not-git",

GET    /api/kanban/projects/:id/cards
POST   /api/kanban/projects/:id/cards       {title?, prompt, agentId, model?, permissionModeId?,
                                             executionMode, baseRef?}
PATCH  /api/kanban/cards/:id                {title?, prompt?, agentId?, model?, permissionModeId?,
                                             executionMode?, baseRef?}
POST   /api/kanban/cards/:id/move           {column}
DELETE /api/kanban/cards/:id

GET    /api/kanban/agents                   可用性检测（which/version）
POST   /api/kanban/cards/:id/start          {restart?: boolean}
GET    /api/kanban/cards/:id/session
POST   /api/kanban/cards/:id/stop
POST   /kanban-hooks/ingest                 {sessionId, event} + x-kanban-hook-token
WS     /api/kanban/sessions/:sessionId/terminal         PTY 字节（二进制帧）
WS     /api/kanban/sessions/:sessionId/agent            ACP 聊天（JSON 文本帧，见 §5.5）
```

错误码（`DomainError`，带 HTTP 映射）：

- `kanban-project-not-found` / `kanban-card-not-found` / `kanban-session-not-found`
- `kanban-project-path-invalid` / `kanban-path-invalid`（不可访问/不是目录/目标非空）
- `kanban-project-duplicate`（同一目录重复添加）
- `base-ref-not-found`（worktree base ref 不存在）
- `kanban-git-command-failed`（`git init` / `git clone` 失败，带 git stderr）
- `kanban-agent-not-installed` / `kanban-agent-profile-missing`
- `kanban-session-not-startable`（列/状态不允许）
- `kanban-worktree-unavailable`（项目根不是 Git 仓库）/ `kanban-worktree-failed`
- `kanban-execution-mode-unavailable`（未知模式）
- `kanban-terminal-unauthorized`（终端 / hook token 无效）

WS 帧错误码（不是 DomainError / HTTP）：`kanban-session-not-terminal`（对 ACP 会话开
terminal WS）、`kanban-session-not-agent`（对 PTY 会话开 agent WS）、
`kanban-session-not-live`（进程已不在本服务端）、`kanban-agent-busy`（上一轮未结束又发
prompt）——都以 `error` / `agent_error` 帧下发。

近实时：看板状态没有接入 `/api/events/stream`（该流只承载 Run 事件），前端用轮询
保持接近实时——每 2s 拉卡片与各会话状态，每 5s 拉项目列表与计数，切回标签页时立即补拉
一次；因此不提供手动刷新按钮。终端字节不走 SSE。

## 九、持久化

- 复用现有 JSON store，新增集合：`kanbanProjects`、`kanbanCards`、`kanbanSessions`。
- 只保存生成时的事实：卡片列/agent/执行模式；session 的 `transport`、状态/时间/退出码/
  nativeSessionId。不保存终端字节与 ACP 聊天记录、不保存进程 pid（内存态）。
- 不读取时兜底：坏记录按 AGENTS.md 视为脏数据，删掉或重建。
- 重启：所有非终态 session → `interrupted`，不自动重跑。

## 十一、验收标准（第一期 Done 的定义）

1. 任意本地目录（无 Git 也可以）能建 BoardProject 并加载看板。
2. 能建卡、选 agent/模型/权限/执行模式（Direct / Worktree）；启动后卡片进 In
   Progress，TUI agent 在终端里出现自己的界面，DSH 出现 ACP 聊天（卡片 prompt 是第一条
   用户消息）；Worktree 卡片的 cwd 是 `dataDir/kanban/worktrees/<sessionId>` 且源工作
   树不变。
3. 终端可输入、可 resize、可 stop；DSH 的聊天可继续发 prompt，刷新页面重新 attach 能
   replay 记录；Cancel 只结束当前 turn（卡片进 Review），Stop / 进 Done 才杀进程。
   stop 后卡片停在 In Progress 且 session 状态可见。
4. Claude / OpenCode 完成一轮 → 卡片自动进 Review（PTY 保持可交互）；用户输入 →
   自动回 In Progress；权限请求 → Needs Attention，不显示为完成。DSH 的 ACP turn 以
   `end_turn` / `cancelled` 结束同样进 Review 且进程保持；聊天里发新 prompt 回 In
   Progress；Ask 模式的权限询问出现在聊天里、答完回 running；Auto-approve 对带 allow
   选项的请求不再询问。Pi 可用 Mark for review 手动进入 Review。
5. 拖拽规则与 §六一致；用户无法把卡片拖到非法列。
6. 重启服务端后：session 全部 `interrupted`，卡片列与项目数据不丢，用户可 restart。
7. 终端 WS 与 ACP 聊天 WS 未携带 token 时都被拒绝；非 loopback 绑定有警告。
8. 现有 `npm run typecheck` / `npm test` 全绿；README 增加 Board 章节与已知边界。

## 十三、已知限制（第一期）

- DSH 没有交互 TUI，ACP app 又是 automation-only：卡片详情能聊天，但没有 DSH 自己的
  plan / todo / 终端卡片呈现，没有 `session/load`（不实现 resume），也没有 DSH 的模型
  选择器（ACP 的 `configOptions` 未接到卡片的 model）。
- 一张卡片同一时刻只跑一个 ACP 进程；聊天记录只在服务端内存，重启后旧卡片的聊天打不开
  （只能 restart 起新会话），`nativeSessionId` 只记录、不续跑。
- 本次改动之前启动的卡片记录没有 `transport`，按纯输出终端展示；按 AGENTS.md 不做数据
  迁移 / 读取兜底。
- 没有 diff / review / commit / PR / checkpoint：Review 列只表示「agent 已完成一轮」，
  不做代码审查。
- 没有自动提交/PR、没有依赖链、没有 auto-review。
- Worktree 只支持「项目根自己就是 Git 仓库」；multi-git / google-repo / 普通目录只能用 Direct。worktree 不自动删除，也不自动 commit。
- 不做 isolated 目录拷贝、Docker 或其他隔离 Runtime；worktree 是第一期的隔离手段。
- 同一 BoardProject 允许多个 Direct 会话并行，平台不加写者锁；并发写冲突由 agent 自己处理。
- 宿主执行：看板不走隔离 Runtime，agent 直接改用户目录（direct 模式）；这是明确的
  产品边界，README 必须写清楚。
- 会话输出不落盘：终端字节与 ACP 聊天记录都只在内存，重启后看不到上一次会话。
- 仅 macOS/Linux 一等支持；Windows 的进程组/终端行为未验证。
