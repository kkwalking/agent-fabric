# AgentFabric 下一阶段修正需求

请基于当前已经完成的 AgentFabric v2 实现继续修正。

当前整体架构方向已经基本确定，包括：

* 已移除统一 AgentFabric Session
* 已采用 RuntimeSessionRef
* 已引入 Runtime Native State
* 已将 Harness Adapter 与 Execution Backend 分离
* Local / Docker 已统一执行通道
* Docker 可以将原始输出交给 Harness Adapter
* Same Harness → Native Resume
* Different Harness → Handoff
* Workspace 与 Runtime Native State 相互独立

本阶段不要重新设计这些已经稳定的抽象。

当前需要重点解决的是：

> **真实 Pi / OpenCode Harness 的协议适配和 Containerized Native Resume correctness。**

---

## 1. 修复 Pi 首次执行使用 `--no-session` 的问题

当前 Pi Runtime 在不存在 Native Session Ref 时，会使用：

`--no-session`

这一行为与 Native Resume 的目标冲突。

`--no-session` 表示本次执行不持久化 Native Session。

这会导致：

Run #1

→ Pi 使用 `--no-session`

→ AgentFabric 获得一个 Session ID

→ Pi 实际没有保存对应 Session State

→ Container 销毁

→ Run #2 使用 `--session <id>`

→ Native Session 无法真正恢复

因此需要修改 Pi 新 Session 的启动行为。

---

## 2. Pi 新 Run 默认创建可持久化 Native Session

当 Pi 执行一个新的 Task / Native Session 时：

不要默认使用：

`--no-session`

而应该让 Pi 使用正常的 Session 模式。

目标是：

Run #1

→ Pi 创建 Native Session

→ Pi 将 Session State 保存到 Runtime Native State Storage

→ AgentFabric 获取 Native Session Ref

→ Container 可以销毁

随后：

Run #2

→ Attach 同一个 Runtime Native State

→ 使用 Native Session Ref Resume

→ Pi 能继续上一轮任务上下文

---

## 3. Pi Native Resume 必须以真实 Harness 行为为准

现有 Fake Pi Test 不应该只根据是否存在：

`--session`

参数就模拟 Resume 成功。

测试需要更接近真实 Pi 行为：

只有当：

* 第一轮真正创建并保存了 Native Session
* Native State Storage 中存在对应状态
* 第二轮正确挂载 Native State
* 第二轮使用正确 Native Session Ref

时，Resume 才应该成功。

避免 Fake Harness 将真实 CLI 不支持的行为模拟为成功。

---

# 4. 重做 Pi Event Protocol Mapping

当前 Pi Harness Adapter 对 JSON Event Stream 的识别与真实 Pi Protocol 不完全一致。

需要按照当前 Pi 的真实 JSON Event 类型重新梳理 Event Mapping。

需要重点支持包括但不限于：

* Session Event
* Agent Start
* Agent End
* Turn Start
* Turn End
* Message Start
* Message Update
* Message End
* Tool Execution Start
* Tool Execution Update
* Tool Execution End

AgentFabric 不需要复制 Pi 的完整协议，但需要将重要事件映射到统一 Event。

---

## 5. Pi Event Mapping 目标

至少保证能够正确产生：

* Agent Message
* Tool Started
* Tool Progress / Output
* Tool Completed
* Run Progress
* Runtime Error
* Usage Information

无法识别但仍有价值的 Pi Event 可以作为 Debug / Raw Event 保留。

不要因为 Docker Execution 而丢失 Pi 原始结构化事件。

---

# 6. 修正 OpenCode Event Protocol Mapping

OpenCode 当前 Native Session Ref 提取逻辑可以继续保留。

但 OpenCode Event Mapping 需要按照真实 `run --format json` 输出重新调整。

需要正确理解当前 OpenCode 的主要事件，例如：

* Text
* Tool Use
* Step Start
* Step Finish
* Error
* Usage / Cost
* Session-related Metadata

不要继续假设 OpenCode 输出的是 AgentFabric 风格的：

* message.*
* tool.started
* tool.completed
* shell.*

Harness Adapter 应负责把 OpenCode 原生事件转换成 AgentFabric Event。

---

## 7. Local 和 Docker 必须共用同一 Harness Parser

继续保持当前已经建立的设计：

Harness Adapter

→ Execution Backend

→ Local / Docker

无论 Harness 是 Local Execution 还是 Docker Execution：

都应该使用同一个：

* Native Session Ref Parser
* Event Parser
* Usage Parser
* Error Parser

Execution Backend 不应该理解 Pi 或 OpenCode 协议。

---

# 8. 打通真实 Usage / Cost Parsing

当前 AgentFabric 已经有 Usage / Cost 数据模型，但 Harness Adapter 需要真正从 Harness 原生输出中提取 Usage。

OpenCode 和 Pi 都可能在结构化事件中提供：

* Input Tokens
* Output Tokens
* Reasoning Tokens
* Cache Tokens
* Cost
* Model Usage

需要将这些数据写入现有 Run Usage 体系。

不能只解析成普通 Event，而不更新 Run Usage。

---

## 9. Usage 应由 Harness Adapter 负责

不同 Harness 的 Usage 数据结构不同。

因此应该由：

Pi Adapter

负责 Pi Usage Parsing。

OpenCode Adapter

负责 OpenCode Usage Parsing。

统一执行层只负责提供 raw output。

最终 Adapter 将标准化 Usage 交给 AgentFabric Core。

---

# 10. 修复 Pi Container 默认镜像策略

当前 Pi Containerized Runtime 不应该默认使用普通：

`node:22-alpine`

因为普通 Node Image 中并不存在 Pi Harness。

Containerized Pi 应满足：

Container 本身已经包含 Pi CLI，并且能够直接作为 Pi Runtime 启动。

当前阶段建议选择一种明确策略。

例如：

### 方案 A

如果用户没有配置 Pi Runtime Image：

直接拒绝启动 Containerized Pi，并提示需要配置兼容 Pi Runtime Image。

或者：

### 方案 B

AgentFabric 提供一个明确的默认 Pi Runtime Image。

不要使用一个实际上没有 Pi CLI 的普通 Node Image 作为 fallback。

---

## 11. 修正 OpenCode 默认 Container Image

检查当前 OpenCode 默认 Docker Image 是否仍然指向旧镜像。

默认 Image 应对应当前实际维护的 OpenCode 官方 / 推荐 Runtime Image。

不要继续使用已经过时的镜像命名。

同时需要保证默认镜像的：

* Entry Point
* OpenCode CLI
* Native State Directory
* Working Directory

与 AgentFabric Docker Executor 的假设一致。

---

# 12. Container Image 与 Harness Execution Contract

需要明确：

一个 Containerized Harness Image 必须满足什么条件。

例如：

* Harness CLI 已安装
* 默认 Entry Point 可以执行 Harness
* Workspace Mount Path 明确
* Native State Mount Path 明确
* stdout/stderr 可以输出 Harness Protocol
* Native Resume 参数可以正常使用

Runtime Image 应被视为 Harness Execution Contract 的一部分。

---

# 13. 收紧 Native Resume 条件

当前不能只根据：

Same Harness

就判断可以 Native Resume。

Native Resume 至少应该要求：

* Same Harness
* Same / Compatible Workspace
* 存在有效 RuntimeSessionRef
* 存在对应 Runtime Native State
* Runtime Capability 支持 Native Resume

---

## 14. Workspace 必须参与 Resume Compatibility

如果一个 Task 首先执行：

Pi

→ Workspace A

→ Native Session X

随后用户继续 Task，但选择：

Pi

→ Workspace B

不应该直接 Resume Native Session X。

因为 Native Session 往往与当前 Working Directory / Project State 有强关联。

因此至少需要：

Same Harness

*

Same Workspace

才能自动 Native Resume。

否则应该：

* 创建新的 Native Session
* 或通过 Handoff / Context Transfer 继续

---

## 15. Resume Compatibility 后续扩展空间

当前阶段至少实现：

Harness + Workspace

Compatibility。

架构上可以为未来预留：

* Runtime Version Compatibility
* Harness Version Compatibility
* Native State Version
* Model Compatibility
* Runtime Configuration Compatibility

但本阶段不需要过度设计。

---

# 16. Runtime Capability 必须反映 Execution Backend 的真实能力

如果 Runtime 声明：

* Supports Native Session
* Supports Native Resume
* Supports Streaming Events
* Supports Usage

那么这些能力必须在当前实际执行方式下成立。

不能出现：

Local OpenCode Supports Native Resume

但：

Docker OpenCode 实际无法 Resume

却仍然向上声明统一的：

`supportsNativeResume = true`

---

## 17. Capability 应考虑组合后的真实能力

真实能力应该由：

Harness Capability

*

Execution Backend Capability

*

Runtime Configuration

共同决定。

例如：

OpenCode Harness 本身支持 Native Resume，

但如果：

* Native State 没有持久化
* Docker Image 不支持正确目录挂载

那么当前 Runtime Instance 不应该被视为真正支持 Native Resume。

---

# 18. 增加真实 Integration Test

当前 Fake Harness Test 可以继续存在，用于验证：

* Orchestrator
* Execution Backend
* Lifecycle
* Native State Mount
* Handoff Routing

但它不能作为 Native Resume 最终验收。

需要增加使用真实 Harness 的 Integration Test。

---

## 19. Pi Native Resume Integration Test

测试目标：

Run #1：

* 使用真实 Pi
* 创建 Native Session
* 修改 / 使用 Workspace
* 保存 Runtime Native State
* 获取 Native Session Ref
* 销毁 Container

Run #2：

* 创建新的 Container
* Attach 同一个 Workspace
* Attach 同一个 Native State
* 使用 Native Session Ref Resume
* Pi 能明确延续 Run #1 的上下文

该测试才表示：

Containerized Pi Native Resume 真正闭环。

---

## 20. OpenCode Native Resume Integration Test

同样需要验证：

Run #1：

* 真实 OpenCode Container
* 创建 Native Session
* 保存 Native State
* 获取 Native Session Ref
* Container Destroy

Run #2：

* 新 Container
* Attach Workspace
* Attach OpenCode Native State
* Native Resume
* OpenCode 继续上一轮任务

---

# 21. Handoff 逻辑保持不变

本阶段不要修改现有跨 Harness Handoff 设计。

Pi → OpenCode：

Handoff。

OpenCode → Pi：

Handoff。

Native State 不跨 Harness 迁移。

RuntimeSessionRef 不跨 Harness 使用。

Workspace 可以继续复用。

---

# 22. 本阶段不要继续增加新的核心抽象

当前这些抽象已经足够：

* Task
* Run
* Workspace
* Runtime
* RuntimeSessionRef
* Runtime Native State
* Handoff
* Execution Backend
* Harness Adapter

本阶段重点不是继续重构领域模型，而是让现有抽象真正正确适配真实 Pi 和 OpenCode。

---

# 23. 本阶段最终验收标准

完成后至少满足以下场景。

### Pi Local Native Resume

Run #1

→ 创建 Native Session

→ Run #2 Native Resume 成功

### Pi Docker Native Resume

Run #1

→ Container A

→ 创建 Native Session

→ Persist Native State

→ Destroy Container A

→ Run #2

→ Container B

→ Attach Native State

→ Native Resume 成功

### OpenCode Local Native Resume

Run #1

→ Run #2

Native Resume 成功。

### OpenCode Docker Native Resume

Container A

→ Native Session

→ Destroy

→ Container B

→ Native Resume 成功。

### Cross Harness

Pi → OpenCode

始终 Handoff。

OpenCode → Pi

始终 Handoff。

### Events

Pi / OpenCode 在 Local 和 Docker 下都能正确产生主要 AgentFabric Events。

### Usage

Pi / OpenCode 的真实 token / cost 数据能够进入 Run Usage。

### Workspace Compatibility

不同 Workspace 不自动复用旧 Native Session。

---

# 24. 核心原则

请继续坚持：

> **Containers are disposable.**

> **Workspaces are durable.**

> **Harness sessions stay native.**

> **Runtime native state is opaque.**

> **Same compatible Harness context means Resume.**

> **Different Harness means Handoff.**

> **Execution Backend transports; Harness Adapter understands protocol.**

本阶段的核心目标不是增加更多 AgentFabric abstraction，而是确保：

> **AgentFabric 在真实 Pi / OpenCode、真实 Local / Docker 环境下，其 Native Resume、Events、Usage 和 Runtime State 行为与产品设计完全一致。**
