# AgentFabric 交互逻辑审查报告

**日期**：2026-10-25
**范围**：Web 界面全部交互面（侧栏、任务线程、看板、设置等），以及打包后的 macOS App
**方法**：逐面读代码 → 在运行中的应用里实测 → 把每个发现固化成打包断言
**结论**：审查覆盖全部主要交互面，修掉 14 类问题，打包验证从最初的 18 项增长到 **58 项（有数据）+ 43 项（空安装）**

---

## 一、为什么要做这份审查

这些改动之前的验证只回答一个问题：**App 能不能启动**。它不回答：用户点下去之后**会发生什么**。

典型例子：`ErrorBox` 组件渲染成 `<div className="card">Error: …</div>`，而验证脚本找的是 `.error-box`。选择器永远匹配不到，于是"页面没有错误"这条检查**从加进去那天起就没检查过任何东西**，却一直显示 `ok`。

这类"静默假通过"是本轮审查最主要的产出目标：**先确保检查本身有效，再去信任它的结论**。

## 三、修掉的 14 类问题

### 功能性缺陷（会导致错误行为）

1. **停止运行失败被静默吞掉**
   `stopRun` 是 `await post(...).catch(() => {})`。点停止看起来生效，agent 仍在跑、仍在计费，屏幕上什么都没有。→ 失败时报错，且仍刷新（run 可能已自行结束）。

2. **重试一次会生成两条 handoff**
   "生成摘要 → 发送"是两次请求，只有第二次可重试。发送失败后用户再点一次，会**再生成一条 handoff**（多一条记录、多一次模型调用，接口不幂等）。→ 记住已生成的状态，重试直接发送；编辑消息则清掉。

3. **卡片删除的"武装状态"跟着切卡走**
   `Delete permanently` 武装后关闭面板、打开另一张卡，那张卡的按钮**直接就是 `Confirm delete`**，一次点击就删掉别的卡。→ 按 `card.id` 重置。

4. **跨任务状态残留（3 处 + 统一修复）**
   `App.tsx` 里 6 个按 id 打开的视图**没有 `key`**，切换任务时复用同一实例：
   - 线程滚动位置：在 A 里上滚看历史，切到 B 后 B 停在顶部，最新消息在屏幕外
   - `handoffReady`：为 A 生成的 handoff 让 B 的首次发送跳过它需要的那个
   - 生命周期页的 `busy`：切换后下一个任务的按钮被禁用到上一个任务请求完成
   → 先逐个重置，再统一加 `key={route.id}` 消除整类问题。

5. **运行取消无错误处理、可连点**
   两处 cancel 都是 `await post(...)`，失败变成未处理的 Promise rejection，界面上没提示；连点会对同一个正在停止的 run 发第二次请求。

6. **两个 cancel 按钮只有一个防重**
   `busy` 是视图级单值，表格里的 cancel 没有守卫：两个请求同时在飞时，先完成的那个清掉 `busy`，让另一个还在进行的请求看起来可再点。

### 一致性问题（体验割裂）

7. **5 处删除用的是浏览器原生 `confirm()`**
   全应用唯一不走 `Modal` 的确认方式。除了样式突兀，原生对话框**会阻塞页面，CDP 自动化点不到**——意味着这些删除流程在打包验证里永远无法覆盖。

8. **阻断提示指向不存在的页面**
   新任务页说"前往 Workspaces 页面"，但该页面已并入 Projects、导航里没有；"LLM 页面""Runtimes 页面"也已是"更多"菜单里的子项。用户照做却找不到地方，表单永远卡住。

### 可观测性缺口（问题不可见）

9. **Docker 状态完全不可见**
   Project 任务只能跑在容器化隔离 Runtime 上。没有可用 Docker 时用户只看到"没有可用的隔离 Runtime"，无法区分**没装**、**装了没启动**、**正常**——三种情况三种修法。→ 新增 `GET /api/docker/status`，分开回答"CLI 是否在 PATH"和"daemon 是否响应"。

10. **未保存的修改会无声丢失**
    设置面板各分区各自维护 `dirty`，面板层不知道。改了字段按 Esc（离开对话框最自然的操作），改动就没了。→ 用 context 上报 dirty，关闭时询问。

11. **全新安装的首次使用是死路**
    空安装里没有隔离 Runtime（内置的都是 host 后端），需要 Docker；而"改选 Project: none"这条路会撞上空的 workspace 选择器，界面上也没有创建 workspace 的入口。→ 提示直接指向 Docker 诊断。

### 验证本身的缺陷（最隐蔽）

12. **错误检测选择器写错，断言从未生效**
    `.error-box` 对不上 `.card`。→ 改为匹配真实节点，并**加一条自校验**：往页面插一个假 ErrorBox，证明检测逻辑看得见它。

13. **所有检查只跑在有数据的夹具上**
    全新安装的空数据路径从未被覆盖——那正是用户第一次打开看到的界面。→ 新增 `--empty` 模式，安装流程连跑两遍。

14. **两处删除一点即删，没有确认**
    `SourceCredentials` 的 remove 直接删掉凭据：存的是 Git token 或密钥，**API 之后不再返回该值**，误删只能去服务商重新签发。`ProjectDetailView` 的 delete 直接删掉项目：它是"代码从哪来"的唯一描述。
    同一应用其他所有删除都走确认，这两处是遗漏。

    修 `ProjectDetailView` 时踩到一个自己引入的 bug：把 `useState` 写在了组件的 early return 之后（`project.error` / `!project.data` 两个提前返回之后）。首次渲染数据未到时少调用一个 hook，数据到达后 hook 数量变化，**Modal 完全不渲染**——类型检查和构建都通过，只有实跑才会发现。

## 四、验证现状

### 两层运行模式

```
npm run desktop:verify        # 有数据的夹具：58 项
npm run desktop:verify:empty  # 空数据目录（全新安装）：43 项
npm run desktop:install       # 安装 App，两遍都跑
```

依赖夹具的 8 个断言块在空模式下**显式跳过**（`if (!emptyMode)` + 块首的 `FIXTURE-DATA ONLY` 标记），而不是留着假装通过。

### 三层护栏（都是踩坑后补的）

1. **旧包警告** —— 安装副本落后于 `packages/web/dist` 时提醒。否则检查的是上一版代码，失败原因看起来像"代码坏了"。
2. **dist 多构建警告** —— 两个 `vite build --watch` 同时写输出目录会让同一视图出现两份 chunk，`index.html` 指向其中一个，**页面静默空白**。
3. **页内错误检测自校验** —— 证明"找错误框"这件事本身有效。

前两层在启动前检查（App 内部任何断言都发现不了这两类问题），第三层在页面内检查。

## 五、方法上的几条教训

这些比具体修复更值得保留：

- **「仅当 X 出现才断言 X」等于给缺陷留后门。** 应写成「X 必须出现」，否则消息缺失时断言会静默跳过。
- **选择器要对着组件源码核对**，不要凭类名猜测。`.error-box` 那个错误因为不报错，藏了很久。
- **反向验证必须走完整打包安装链路。** 改了本地 `dist` 但没重装，验证的是上一版——会得到假失败，也会得到假通过。
- **页面空白或找不到预期元素时，先查 `dist` 是否被并发构建污染**，再怀疑组件代码。
- **修改一类问题后想清楚是否有同类。** `stopRun` 的静默失败在 Runs 页还有两处；`stickBottom` 的跨任务残留还有另外两个状态；「删除没确认」修了 5 处原生 `confirm()` 之后，仍漏了 Project 和凭据两个按钮。
- **React 的 hook 必须写在任何 early return 之前。** 把 `useState` 放在 `if (!data) return …` 后面，类型检查、构建、lint 全过，运行时却让 Modal 永不渲染——hook 数量随数据到没到而变。这类问题只有实跑才发现。
- **断言里的「找到 0 个」必须判失败。** 写过一条「遍历所有页面，确认每个危险按钮都有确认」，第一版在 `across 0 page(s)` 下通过了；也写过一条正则 `\bdanger\b` 放在模板字符串里，被解释成退格符，全部匹配落空。两者都会让检查看起来健康。
- **报告里的数字要能从代码树重新推导。** 初稿照抄了会话笔记，两处数字是错的（视图计数、跳过块计数）；断言数从 57 变 58 后，报告也要跟着变。

## 六、审查中确认"没有问题"的地方

如实记录，避免下次重复审查：

- **回收站没有永久删除入口** —— 刻意设计：删除由服务端 30 天后台清理，页面上写明。恢复失败会报错。
- **`general` 设置分区没有保存按钮** —— 语言切换立即生效（存 `localStorage`），服务端地址和数据目录只读展示。
- **`NewTask` 的提交守卫** 与按钮 `disabled` 完全一致。
- **`BoardTerminal`** 的连接生命周期：`fit` 只在容器真正布局后执行（`display:none` 或 0×0 会算出 2×1 的假尺寸破坏 TUI）、xterm 拒绝非法几何时等待下次 resize、`disposed` 标志防卸载后操作。
- **看板终端的空状态**：Backlog 列提供 Start，其他列说明恢复路径（`Restore to Review` / `Move it to Done`）。规则是"不能是死胡同"，不是"必须有按钮"。
- **有列表的视图都有空状态处理**（17 个视图文件里，`RailMenu` 是导航菜单、`TaskLifecycle` 是单任务详情页，这两个没有「列表为空」的场景）。
- **`ResourceView` 的 `workspaces` 配置没有被路由**：Workspaces 已并入 Projects，这个 kind 是重构后留下的死配置。它不产生任何用户可见行为，删它属于清理而非修 bug，故记录在此而不计入问题清单。
- **所有按钮都有可访问名称**（脚本解析每个 `<button>` 开标签 + 后续文本，无名称的为 0）。

## 七、仍未解决

1. **空安装下没有不依赖 Docker 的可用路径。** 当前是"明确提示"而非"绕过"。是否允许用 host runtime 跑 Project 任务，是产品决策。
2. ~~`desktop:dmg` 偶发卡在 hdiutil 收尾~~ —— **根因已查明，不是 hdiutil**。构建实际早已完成（dmg 写出并通过校验），是**进程不退出**：`verifyApp` 在构建进程内运行，它的 PTY 往返在 macOS 上会留下一个 `/dev/ptmx` 句柄（node-pty 在子进程被杀后不关闭父侧），事件循环因此不空，进程就一直挂着——看起来和 hdiutil 卡住一模一样。`desktop:install` 之所以正常，是因为它 spawn 子进程，句柄随子进程释放。修法：成功路径末尾显式 `process.exit(0)`，并给 `hdiutil create` 补上缺失的超时（attach/detach 早有）。实测：同一构建从挂 10 分钟不结束变为 **19 秒退出、退出码 0、无残留进程**。
3. ~~滚动位置那条缺陷只有浏览器验证~~ —— 已补上打包断言：夹具里给两个任务各造了一条 60 消息的长线程，检查「在 A 里滚到顶部后切到 B，B 停在最新消息」（现为 58 项中的一条）。
